## 三、关键发现：Triton 3.6.0 / sm121 `dot_scaled(e2m1)` 三个实机硬约束

生产侧用最小探针逐项实证（§三节内容，**与 v10 假设/文档字面相反**）：

| # | 硬约束 | v10 原样（错） | 生产修复（对） |
|---|---|---|---|
| 1 | **rhs 布局必须是 `[K, N]`**（Triton 源码 `K_RHS, N = rhs.shape[-2:]`，rhs 第一维是 K） | `rhs_packed [BN, BK//2]`（N 行 K 列）→ `PACKED_B_DIM ≠ PACKED_A_DIM` 断言挂 | W 解包后**不 trans**，`w_full [BK, BN]` → reshape `[BK//2, 2, BN]` → `trans(0,2,1)` → `tl.split` → `rhs_packed [BK//2, BN]` |
| 2 | **scale 必须是 uint8 e8m0 原始字节**（fp32 scale 触发 `TritonGPUAccelerateMatmul` MLIR 崩溃，Triton 3.6.0 bug） | `lhs_scale_fp = exp2(...)`、`rhs_scale_fp = exp2(...)` | 直接传 **uint8 编码字节**（`lhs_scale_u8` / `rhs_scale_u8`）；A 归一化仍用解码值 |
| 3 | **rhs_scale 不 `tl.trans`**（trans 后 scale 触发 codegen bug） | `tl.trans(ws_fp)` 成 `[BN, GROUPS_K]` | 直接按 `[BN, GROUPS_K]` 布局 load（指针维度序交换：`n_groups[:,None]*stride_ws_n + kg_local[None,:]*stride_ws_k`） |

**组合验证**：修复后所有 BLOCK 尺寸（M/N 64/128/256，BK 64/128）均编译运行 OK。

## 四、v11 增量修复（本交付包）

在合并生产修复版基础上，统一**量化舍入**——消除剩余 0.0% 边界失配的根因：

| 文件 | 修复 |
|---|---|
| kernel① triton | 阈值链 `>=` → `>`（等距取低档） |
| kernel② linear triton | 阈值链 `>=` → `>`（K/V 两段） |
| kernel② paged triton | 阈值链 `<` → `<=`（等距取低档） |

**根因**：triton 阈值链原用 `>=`/`<`（中点取高档），torch 参考用 `argmin`（等距取低档，如 0.25 → 0.0）。两者仅在精确中点（0.25/0.75/1.25/1.75/2.5/3.5/5.0）差一档 → 触发 M=894 单行 156 元素、T=4096 的 3 字节失配。统一后**所有 triton 与 torch 参考逐字节一致**，预期 T2 全 PASS。

## 五、性能问题分析：~20 TFLOPS 的根因与调优方向（kernel①）

### 5.1 现状
16.6~20.8 TFLOPS 是 **fp32 级水准**，距 FP4 dense 500 TFLOPS / 验收 400 差一个量级。avg speedup 10× 仅来自 vs torch 参考（1~3 TFLOPS）。

### 5.2 两个关键怀疑（需实机验证）
1. **dot_scaled 是否真正触发 `mmaf_scaled`/FP4 MMA**（而非降级到 fp32/bf16 MMA）——**必须查 SASS 确认**：
   ```bash
   # 找到编译缓存里的 cubin/sass（TRITON_CACHE_DIR 或 ~/.triton/cache）
   nvdisasm -c <kernel.cubin> | grep -iE "mma|tcgen|e2m1|fma" | head -50
   # 期望看到：mma.sync.aligned.m16n8k32.f32.e2m1.e2m1 / tcgen05.mma（sm121 形态）
   # 若只有 FFMA/FMA → 降级路径，需换 Triton 版本或 CUTLASS
   ```
2. **量化开销占比**：每 k-tile 内做 A 全 tile 的 32 组 max/exp2/除法/7 层 where/打包 + W 解包重打包——这些是标量 ALU 密集操作，在 MMA 之前执行，可能吃掉大半时间。GB10 只有 128 SM，小块（BM≤128, warps=4）下 MMA 占比更低。

### 5.3 调优方向（按优先级）
| 优先级 | 动作 | 预期 |
|---|---|---|
| P0 | **SASS 确认**（上一步）——先确定 MMA 指令形态 | 决策依据 |
| P1 | 若 FP4 MMA 已生效：恢复大 BLOCK（BM=128/256, BN=128/256）+ GROUP_M=8/16 + num_warps=8/16 + num_stages=4，减少量化调用次数（BLOCK_K=128 或 A 预量化一次复用） | 200~400 TFLOPS 可期 |
| P2 | 若降级：升级 Triton（修 `TritonGPUAccelerateMatmul` uint8 scale codegen bug 的版本，如 3.7+ nightly），或用 CUTLASS 手写 `mmaf_scaled` 路径替代 | 恢复 FP4 峰值 |
| P3 | 评估 **A 离线预量化**（prefill 大 M 场景）：`quant_kernel` 与 `gemm_kernel` 分离，GEMM 纯 MMA | 消除量化开销（需多一次内存往返，GB10 带宽 273GB/s 内） |
