## 二、kernel② v12 mismatch 根因（49.3% = 恰好一半数据）

生产实测 49.3% mismatch、最大差 255——**数值上等于 K/V 各后 256 元素完全未写**。根因：

```
MCP v2 生成器（被我 v12 原样采纳）：
  grid 第二维 = 32；is_v = pid_g >= 16；g_half = pid_g - 16*is_v ∈ [0,16)
  → K 只处理 col [0:256)（16 组），V 只处理 col [512:768)（16 组）
  → K 后 256 元素 + V 后 256 元素 + 对应 scale 全部缺失 = 49.3%
MCP 服务端 verify total_tests=0（未数值比对）→ 未抓出；生产 pytest 暴露。
```

**修复（v12.1）**：
```
grid 第二维 32 → 64（K 32 组 + V 32 组）
is_v: pid_g >= 16 → pid_g >= 32
g_half: pid_g - 16*is_v → pid_g - 32*is_v（0..31）
```
信封布局推导核对：K `[0:512]→packed[0:256]+scale[512:544]`、V `[512:1024]→packed[256:512]+scale[544:576]`、pad `[576:584]` —— **与 v11/vLLM PR#46329 完全一致**。

## 三、kernel① v12 状态深析

### 3.1 正确性：8/8 全 PASSED ✅（重大突破）
v8 无法编译 → v10 6/8 → v12 **8/8**：舍入统一（`>` 等距取低档）彻底解决了 M=1024/N=2048 的量化边界问题。**defect-to-deployment 闭环达成**。

### 3.2 性能：benchmark 1.7~4.3 TFLOPS（低，但非内核问题）
benchmark 脚本测的是 `triton_impl` **整次调用**，其中含主机侧 torch 操作：
```
_repack_w_for_rhs_k_pack（W [K,N//2]→[K//2,N]，torch 层，M=1024 时约 8~16GB 搬运）
_expand_w_scale（W_scale [K//32,N//128]→[N,K//32]，torch repeat+trans）
```
v12 架构设计是**每层只做一次**（vLLM `process_weights_after_loading()` 缓存），不应计入每次 forward。**生产部署缓存后 GEMM 为纯 dot_scaled MMA，预期显著高于 v11 的 16.6~20.8 TFLOPS**。

**验证方法**（生产上区分内核真实性能）：
```python
# 缓存 W 变换（每层一次）
W_packed_rhs = _repack_w_for_rhs_k_pack(W_packed, K, N)
W_scale_rhs = _expand_w_scale(W_scale, K, N)
# forward 只跑 GEMM kernel（不含 W 变换）→ 计时即为内核真实 TFLOPS
```
若仍低 → 需 SASS 确认 mmaf_scaled 是否生效（P0）。
