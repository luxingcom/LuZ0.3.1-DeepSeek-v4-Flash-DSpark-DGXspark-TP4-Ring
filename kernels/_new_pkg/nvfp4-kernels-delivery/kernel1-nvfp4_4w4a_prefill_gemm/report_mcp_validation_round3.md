## 二、关键发现（本轮验证的价值）

### 1. dot_scaled 三硬约束在 MCP 服务端被二次确认 ✅
kernel① 生成器完全遵守：rhs `[K//2, N]`（K 向打包）、scale 传 uint8 e8m0 字节、rhs_scale 不 trans（`[BN, GROUPS_K]` 直接 load）→ passed + 2.79×。**与生产实机修复（v11）完全一致**，交叉验证通过。

### 2. 生成器自动采用更优架构（kernel①，值得采纳）
```
旧（v11 生产版）：GEMM kernel 内每 k-tile 做 A 量化 + W 解包重打包（量化开销吃时间 → 20 TFLOPS）
新（MCP v3）    ：分离式 —— ① _quantize kernel（A→A_packed+A_scale，一次）
                   ② 主机侧 _repack_w_for_rhs_k_pack（W [K,N//2]→[K//2,N]，每层一次可缓存）
                   ③ _expand_w_scale（[K//32,N//128]→[N,K//32]，每层一次）
                   ④ GEMM kernel 纯 dot_scaled MMA（无量化开销）
```
这正是生产报告 §五 P3 建议的方向，MCP 生成器自动实现了——**v12 应采纳此架构**。

### 3. MCP 生成器 scale 语义再次偏离标准（必须修正，不可直接用）
| 生成器 | e8m0 字节 | 归一化 | 问题 |
|---|---|---|---|
| kernel① v3 | `floor(log2(max)) + 127`（**丢 /6**） | x/2^floor(log2 max) ∈ [1,2) | 只用 E2M1 下半码本（0~2），精度损失 ~2.6 bit |
| kernel② v2 | `floor(log2(max/6)) + 127`（**对**） | x/(2^(e8m0-127)·6) ∈ [1,2) | scale_factor 多乘 6，归一化值域偏移（e8m0 字节正确） |
| 标准 NVFP4（v5/v11） | `floor(log2(max/6)) + 127` | x/2^floor(log2(max/6)) ∈ [1,6] | 全码本 ✅ |

> 再次印证：**MCP passed=True ≠ 语义与标准一致**（其 verify total_tests=0，未做数值比对，仅脚手架级通过 + benchmark 计时）。生成器"自洽但非标准"是常态，交付前必须语义 diff。

### 4. paged：harness 不兼容 + 生成器布局错误
- 8 轮全挂 `NameError: torch not defined`——MCP harness 对 6 参 in-place 签名不兼容（生成器代码本身 import 完整）
- 生成器把 584B 信封排成 `[K_data(256), K_scale(32), V_data(256), V_scale(32), pad(8)]`——**与 vLLM PR #46329 / 生产 v5 的 `[K_data(256), V_data(256), K_scale(32), V_scale(32), pad(8)]` 不符**，弃用
- **paged 维持 v11 修复版**（生产 5/5 全精确）——无需 MCP 重生成
