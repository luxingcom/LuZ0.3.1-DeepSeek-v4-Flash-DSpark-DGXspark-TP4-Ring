## 3. 瓶颈定位：不是显存、不是网络、不是节点——是**768K 单流串行 + 访存延迟受限**

### ⚠️ 重要修正（2026-08-12 二次核查）："UMA 带宽 0%" 是假象

初版分析中 `nvidia-smi dmon mem=0%` 被误读为"带宽未饱和"，**经用户质疑后核查确认该指标在 GB10 上无意义**：

| 证据 | 结果 |
|---|---|
| dcgm-exporter 指标清单 | **无 DRAM 带宽指标**；MEM_COPY_UTIL=0 / MEMORY_TEMP=0 / DEC_UTIL=0 均为独立显存架构专属，UMA 下全部无效 |
| nvidia-smi dmon -s pmt | mtemp/fb/rxpci/txpci 列全为 `-`（无独立显存控制器可监控） |
| **sudo perf mem_access PMU** | 10s 全系统 **100.4 亿次内存访问**（~100亿次/s）；按 64B cacheline ≈ **643 GB/s 有效带宽**——UMA 带宽真实存在且繁忙！ |
| CPU 侧实测（Python 大数组） | 读 **436 GB/s** / 写 113 GB/s |

**结论**：GB10 是统一内存架构，GPU 无独立显存控制器 → `nvidia-smi` 的显存带宽列恒为 `-`/0，**判断内存带宽必须用 PMU `mem_access` 或业务反推**。

### 排除项（修正后）

1. **不是显存容量**：KV cache 仅用 17-18%，74GB 显存余量巨大
2. **不是网络**：总带宽 22GB/s，但 decode 每 token 通信仅 ~368KB；all-reduce 早已与计算重叠
3. **不是节点短板**：四机 util/功耗/CPU 完全均衡
4. **不是带宽饱和**：UMA 有效带宽实测 ~643 GB/s（PMU），而业务需求仅 185 GB/s（并发4重叠）——带宽有余量

### 根因分析（三层）

**① 负载形态：超长上下文 + 极低并发 = 单流串行**
- 768K ctx 意味着每步计算的是**整条 768K 序列的注意力/MLP**，decode 每步的计算量巨大
- 并发仅 4-5，vLLM 批大小小 → **GPU 无法并行消化多个请求**，SM 虽有活干但每个 kernel 很小
- TTFT 96s 完全由 768K prefill 的串行计算决定

**② 投机解码的"草稿瓶颈"**
- 日志显示 Drafted 仅 4-5 t/s——**投机草稿模型本身每步也要跑完整 768K 上下文注意力**，草稿不"便宜"
- 768K 上下文下，草稿模型 + 验证模型都要访问全量 KV → 投机收益被上下文长度稀释（原设计假设短上下文）

**③ "SM 96% + 功耗 55W + 带宽有余量" 的真实含义（修正后）**
- 量化：768K ctx 的 MLA KV = 768K × 6.7KB ≈ **5.1GB**；TPOT=111ms/步 → 单步遍历 5.1GB ≈ 46 GB/s（并发 4 重叠 ~185 GB/s），**远低于 UMA 实测 643 GB/s 上限**
- 即带宽**没有**饱和，但**每步必须串行遍历 5.1GB KV** 才能算注意力 → **瓶颈 = 访存延迟 × 串行依赖（memory-latency-bound）**：SM 利用率高是"在等数据"，功耗低是"算力闲置"，mem 0% 是指标缺失
- 与短上下文场景（KV 小，带宽主导）不同：768K 下是**每次遍历的延迟**主导

## 4. 结论

**当前瓶颈 = 超长上下文（768K）单流场景下的"顺序 decode 步延迟"**，具体链条：

```
768K KV → 每步全量注意力（内存延迟主导）→ 步延迟 ~111ms（TPOT）
× 低并发（4-5 req）→ 无法并行摊薄 → 聚合吞吐仅 4-6 t/s
```

这不是集群配置问题（四机 TP4 工作正常、均衡、网络/显存/内存带宽均有大量余量），而是**测试负载本身的形态决定的**：768K ctx + 低并发 = 单流延迟受限场景。

## 5. 优化方向（按收益排序）

| # | 措施 | 预期收益 | 说明 |
|---|---|---|---|
| 1 | **提高并发**（8-16） | 聚合吞吐可到 10-20 t/s | 并行摊薄步延迟；并发收益分界在 16K-32K ctx，768K 下更显著 |
| 2 | **缩短上下文**（128K/64K） | TPOT 大幅下降 | 768K 是极端测试，生产负载通常远小于此 |
| 3 | 检查投机配置：768K 下考虑禁用/调低 draft 数 | 释放草稿模型的计算 | Drafted 4-5 t/s 与主模型同速，说明草稿未带来加速 |
| 4 | MTP/更多投机步数 | 若草稿"便宜"才有效 | 当前 768K 下草稿不便宜，先测 3 |
| 5 | 核绑定优化（IRQ 移出 5-9） | 微幅降低抖动 | 非当前瓶颈 |

## 6. 一句话总结

**四机 TP4 集群本身健康、无短板、资源充裕（显存余 80%+、带宽余 90%+）**；当前 4-6 t/s 的低吞吐是 **768K 超长上下文 + 低并发**负载的固有形态（每步 768K 注意力延迟主导、并行度低），瓶颈在"负载形态"而非"硬件配置"。**提高并发是当前立即可得的最大收益点**。
