## 0. 执行摘要（四项各一句话）

1. **研究一（threshold 2048 异常）**: 对 A/B 原始轮次数据再分析发现**头号根因候选是实验混杂而非 threshold 效应**——同配置 threshold-1024 的两次运行结果相差 26 个百分点（rollback 臂 -24.5% vs armA +2.0%），且 2048 臂内部双峰（快轮 2552 tok/s ≈ Roofline 预测 +18%/token，慢轮 +~200ms/步）；真正的每步时间比为 2.06-2.17×（线性预期 2.0×），说明存在小幅（+3-8%/token）的真实回归 + 大幅随机方差，二者必须用带仪器复测分离。NCCL 16.8MB>8MB 候选**源码级降级**（4 通道下单通道数据 4.2MB < 8MB，无协议边界）。复测协议见 §1.5。
2. **研究二（workspace 去重）**: **关键口径修正**——生产 W4A16 路径（`--moe-backend flashinfer_b12x` → 社区 b12x 包 `B12xExperts`）的 scratch 走 vLLM 全局 `WorkspaceManager`，**已经跨 43 层共享，无重复分配**；×43 重复分配专属 **FlashInfer wrapper 路径（`FlashInferB12xExperts`，nvfp4/W4A4 量化）**——每层 lazy 创建 `B12xMoEWrapper` 各自持有 ~0.3-0.65GB workspace，这正是 W4A4 实验 +28GB/+42GB No-Go 的结构性根因。fork 内自做方案 = 在 `flashinfer_b12x_moe.py` 加模块级几何键共享池（~60 行补丁，2-4 天），伪代码见 §2.5；它解锁的是 W4A4/W4A8 路线而非当前生产。
3. **研究三（FlashInfer 0.6.16）**: 遗留验证完成——镜像内 0.6.15 **确实是补丁混合版**（94 处路径差异：64 个修改文件 + 30 个独有文件），但形态是「0.6.15 基底 + 0.6.16-dev 回移」（64 个修改文件中 41 个已与 0.6.16 逐字节相同；独有文件如 fmha_blockscaled.py/moe_lora_delta.py 与 0.6.16 完全相同）。**b12x 树（b12x_moe.py + moe_dispatch.py）完全未被补丁**。0.6.16 的 `B12xMoEWrapper` API 签名不变、依赖全满足（cudnn-frontend 1.26≥1.25）、torch 无 pin。升级真实工作量 = 重放 23 个自定义冲突文件 + 核对 ~15 个分歧回移文件，**1-2 周可行**。
4. **研究四（attention b12x 化）**: Eugr 配方完整考证（vLLM main 08-05 dev + SparkInfer 1.0.1 + V2 model runner + AOT compile + 全套 B12X env）。fork 内 **零** B12X attention 组件（只有 VLLM_USE_B12X_MOE 一个 env）。社区关键警示：有用户报告 **b12x MoE 在 GB10 上 prefill stall**（改用 cutlass W4A8 但保留 b12x attention）、WO_PROJECTION 在高并发下不稳定。且 kernel 单挑被 b12x 包版本锁死（attention 栈需要 ≥1.0.x，与 torch 2.11 冲突待核）。**建议：不动生产 fork，先做 Eugr 镜像并行 A/B（零 fork 改动）再决策**。

## 1. 研究一（P1）：threshold 2048 异常源码级根因分析

### 1.1 新证据：A/B 原始数据再分析（混杂因子发现）【实证-数据】

在服务器 `/tmp/_routea_work/` 找到 08-22 当天 threshold 实验全部原始轮次数据（此前报告只引用了汇总行）：

| 臂 | threshold | 4K 档（8.2K 真实 tokens）轮次 TTFT | PR 中位 | Δ vs 基线 2510 |
|---|---|---|---|---|
| bench_rollback（05:59，带 10× warmup） | **1024** | 4.6 / 4.3 / 4.3 s | 1895 | **-24.5%** |
| armA（06:47） | **1024** | 3.5 / 3.2 / 3.2 s | 2561 | **+2.0%** |
| armB（07:00） | **2048** | 4.3 / **3.2** / 4.1 s | 1986 | **-20.9%** |

三个决定性观察：

1. **同配置反差**：rollback 臂与 armA 同为 threshold 1024、同镜像、同为重启后冷启动，45 分钟内结果相差 26 个百分点（-24.5% vs +2.0%）。rollback 臂的 serve 命令经核验（`rb_final_head.log`）确为 1024。⇒ **存在一个与 threshold 无关、随时间漂移的 ±20% 级混杂因子**（候选：同节点 aicad 服务 CPU 竞争的时段性、JIT/编译缓存状态、节点状态；pr-de 报告 E2 已实证 aicad 竞争造成 -4%）。
2. **2048 臂内部双峰**：轮 2 快达 2552 tok/s（= armA 水平，且 per-token 390μs→320μs = **-18%，恰为 Roofline 预测 +15-20% 的方向与量级**），轮 1/3 慢至 ~1900。回归不是均匀的。
3. **DE 完全不受影响**：armA/armB 的 C12 decode 聚合吞吐 369.1 vs 370.0 tok/s（`de_armA.json`/`de_armB.json`）——**效应是 prefill 特有的**，排除全局性节点劣化作为 armB 慢轮的全部解释。

**每步时间核算**（8.2K prompt：1024 档 8 步、2048 档 5 步）：

| 档位 | 1024 档步时 | 2048 档步时（慢轮） | 比值 |
|---|---|---|---|
| 8.2K | 400 ms | 866 ms | 2.17× |
| 32.8K | 405 ms | 866 ms | 2.14× |
| 65.5K | 421 ms | 870 ms | 2.07× |
| 131K | 454 ms | 936 ms | 2.06× |

线性组件（MoE/AR/attention/dense 全部随 M 线性）预期步时比 = 2.0×。实测 2.06-2.17× ⇒ **真实回归成分只有 +3-8%/token**（慢轮口径），快轮（3.2s/5 步 = 640ms/步）则是 -18%/token。即：threshold 2048 的"净效应"= Roofline 收益（-18%/token）− 小额真实回归（+3-8%/token）− 大额随机方差（±25% 请求级）。**-22.5% 的原结论主要由方差/混杂贡献，不能作为"扩 M 劣化"的定论。**

### 1.2 源码分析：scheduler 与 threshold 的交互【实证-源码】

生产启动参数（docker inspect）：`--max-num-batched-tokens 4096`（token_budget）、`--long-prefill-token-threshold 1024`、`--max-num-seqs 12`、dspark n=7。启动日志另有告警：`max_num_scheduled_tokens is set to 4024 based on the speculative decoding settings`。

- **`v1/core/sched/scheduler.py:507-508`**（running 队列，续算 chunk）：`if 0 < long_prefill_token_threshold < num_new_tokens: num_new_tokens = threshold`；随后 `min(num_new_tokens, token_budget)`。**:861-863**（waiting 队列首 chunk）同逻辑。⇒ threshold 只钳制单请求单步 chunk；1024/2048 均远小于 budget 4096，两臂每步均为单 chunk + 可选 decode 混批（≤12×8 spec tokens）。
- chunk 结构：8203 tokens @1024 = 8×1024+11（尾块 11）；@2048 = 4×2048+11（尾块 11）。**两臂步数 8→5**，尾块同为 11（轮间 ±1 因 nonce 分词）。
- 调度交互结论：decode 穿插频率减半属二阶效应；C12 decode 实测两臂相同（§1.1 观察3）⇒ 候选③（chunked-prefill 调度交互）**降级为次要**。

### 1.3 三候选逐一源码评估

**候选②（NCCL 16.8MB > 8MB buffsize 协议切换）——降级**【实证-源码+实证-数据】
- 生产 NCCL 环境（docker inspect）：`NCCL_BUFFSIZE=8388608`、`NCCL_MIN/MAX_NCHANNELS=4`、`NCCL_ALGO=RING`、`NCCL_TUNER_THRESHOLD=40960`、ring-only 定制库（`LD_PRELOAD=/opt/nccl-ringonly/libnccl.so.2`，pip nccl 2.30.7）。
- NCCL 日志（容器 `/var/log/vllm/nccl-node01.log`，生产已开 NCCL_DEBUG=INFO）：4 通道 ring、`P2P Chunksize set to 262144`。
- 消息尺寸核算：单次 AR = M×4096×2B。M=1024 → 8.39MB，4 通道均分 2.1MB/通道；M=2048 → 16.8MB，均分 4.2MB/通道。**两者单通道数据均 < 8MB buffsize，均单 chunk 完成，不触发多 chunk 流水；两者均远大于 LL/LL128 切换点（深 Simple 区）与 tuner 阈值 40960（均走默认路径）**。⇒ "16.8MB>8MB 引起协议切换"在源码/配置层面不成立。保留角度：更大单消息对 RoCE 拥塞/重传（NCCL_IB_RETRY_CNT=7）的暴露概率——交由复测的 RDMA 计数器判定。

**候选①（激活峰值/KV 驱逐）——降级**【实证-源码】
- MoE scratch 与 M 解耦：生产走 `B12xExperts`（见 §2.2 路径考证），scratch 由全局 WorkspaceManager 按 **max_num_tokens=4096**（= max_num_batched_tokens）一次性规划（`modular_kernel.py:1078-1094` → `workspace.py` 单例缓存），**threshold 1024/2048 下 scratch 大小不变**。
- 逐步瞬时激活（hidden bf16 等）在 M=2048 约 2× 但绝对量仅几十 MB；`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 使增长为一次性映射。KV 池固定（6.0M tokens），无证据触发驱逐/重算（日志无 preemption/recompute 行，docker logs 全量 grep 仅 20 条无关 WARNING）。
- 残余角度：workspace2 首次遇到 M=2048 plan 时 Manager resize 一次性 empty_cache+重分配——一次性行为，可由复测的内存曲线证实。

**新候选④（形状触发的 JIT/launch 特化 + 实验方差）——升为头号**【实证-源码+实证-数据】
- 生产日志实证推理期 JIT：`WARNING [jit_monitor.py:135] Triton kernel JIT compilation during inference: _compute_global_topk_indices_and_lens_kernel`（07:22:58）与 `_prepare_dflash_inputs_kernel`（07:24:03）——本栈存在推理期按形状懒编译的既成事实。
- b12x 包 launch 按 token 数特化【实证-源码】：`b12x/integration/tp_moe.py:182/186`（`planned_token_counts`、`planned_fused_moe_launches` 按 capacity 键控）；fork 桥接层 `b12x_mxfp4_moe.py:61` 每次apply 以**当前步 token 数**为 `core_token_counts` 传入（`frozen=True`）⇒ 新 token 数首遇需 materialize+prewarm（Triton route-pack 有模块级 `_W4A16_ROUTE_PACK_PREWARMED` 全局缓存 :65，CuTeDSL 走内核级编译缓存）。launch 查找是 capacity≥语义（tp_moe.py:2438-2443），**frozen 模式下未规划的 token 数会直接 RuntimeError**（:2444-2447）——生产未崩说明全部覆盖，但首遇成本真实存在。
- 关键佐证：上游 b12x #226（commit 56ab5f4）"reuse fixed route arenas for prefill tails，避免每个 tail 长度触发新 Triton 特化编译"——**上游正是为同类问题打的补丁**【实证-上游】。
- 间接反证（诚实标注）：armB 轮 3（ptok 8204，尾块 12）在轮 2（尾块 11）之后仍慢、rollback 臂三连慢，无法用"每形状一次 JIT"完全解释 ⇒ JIT 候选解释部分慢轮，**其余慢轮归因于 §1.1 的环境方差混杂**。二者叠加与观测双峰/持续慢形态吻合。
- 附加发现【实证-源码】：`--enable-flashinfer-autotune` 在 GB10 上**实际无效**——`model_executor/warmup/kernel_warmup.py:130`：autotune 仅 `has_device_capability(90)`（Hopper/Blackwell SM90/100）执行，SM121 被跳过；MHC TileLang 预热覆盖 1..16384（含 1024/2048，`deepseek_v4_mhc_warmup.py:26-39`）不受影响。

### 1.4 根因候选排序（更新版）

| 排名 | 候选 | 证据强度 | 判定路径 |
|---|---|---|---|
| **1** | **实验混杂/方差**（同配置 ±25% 漂移：aicad 时段性竞争、节点状态等） | 强（rollback vs armA 反差；DE 不受影响排除全局劣化主导 armB） | 复测协议 §1.5 的交错 A/B + 同窗对照 |
| **2** | **形状首遇 JIT/launch 特化**（M=2048 及尾块新 token 数的 materialize+prewarm） | 中强（jit_monitor 实证同类行为；上游 #226 同病；解释 armB 轮1/轮3） | 复测时 jit_monitor 时间戳对齐慢轮 |
| 3 | 小额真实回归（+3-8%/token，慢轮口径）| 中（步时比 2.06-2.17× > 2.0×） | torch profiler 逐步分解 |
| 4 | NCCL 16.8MB>8MB 协议切换 | 弱（源码核算无边界效应） | RDMA 计数器排除/确认 |
| 5 | 激活峰值/KV 驱逐 | 弱（scratch M 无关；无 preemption 日志） | 内存曲线监控排除 |

**结论**：扩 M 实验应**重启**——快轮证据（2552 tok/s、-18%/token）支持 Roofline 方向；但必须先按 §1.5 协议把方差与 JIT 从信号里剥掉，否则任何 A/B 结论都不可信（本异常本身就是教训）。

### 1.5 带仪器复测协议设计（供窗口代理直接执行）

**总原则**：交错 A/B（消除时间漂移）+ 每请求全仪器同采 + 足够轮数（≥10/臂）+ 慢轮即时归因。

**P0. 交错 A/B 框架**
- 两个臂各重启一次后，**不再切换配置**，改用「同一进程内由请求长度间接控制 M」：不动 threshold，改用两组 prompt——8.2K（8 步 chunk=1024）与 8.2K+1024（前 4 步 chunk=1024 后 4 步 1024…不可行时退回双容器交错）。若必须双臂：A(1024)→B(2048)→A→B 各 10 轮 4K 档，同窗口完成，记录每轮时间戳。
- 每轮输出：TTFT、prompt_tokens、轮时间戳（对齐下面的仪器时间线）。
- 判据：①两臂各自轮间方差的量级（若 A 臂自身 ±20% 则混杂主导，停止归因 threshold）；②剔除首 2 轮（冷/JIT）后中位对比。

**P1. JIT/编译监测（判候选④）**
- 生产已内置 jit_monitor（日志 grep `JIT compilation during inference`）——复测期间实时采集时间戳。
- 采集 `B12X_PRINT_COMPILE_PROGRESS=1`（b12x 0.15.3 支持，upstream 报告 §2.E）观测 b12x 编译事件。
- **预期信号**：慢轮 TTFT 与 JIT 告警时间戳强相关 ⇒ 候选④成立；无相关 ⇒ 排除。
- 附加：把 warmup 改为「覆盖 M=1024 与 M=2048 各 3 次 + 尾块 8/9/10/11/12/13 各 1 次的真实 prefill」（替换现在只 warm 短请求的做法，arm0a_bench.sh 的 20×'Hello'×50 warmup 对 prefill 路径无效）。

**P2. RDMA 计数器同采（判候选②残余）**
- 复用 `prde_bn_evidence*.sh` 的 200ms 采样脚本（/sys/class/infiniband/*/ports/1/counters，4 口）。
- **测什么**：每步 tx/rx octets 是否随 M 超线性（AR 总量两臂应相同）；重传/错包计数器（port_xmit_discard、port_rcv_constraint_errors 等）是否在慢轮时间窗内跳升。
- **读法**：AR 量不变 + 无错误跳升 ⇒ 候选②彻底排除；错误跳升 ⇒ 拥塞/重传路径。

**P3. 逐步计时与 dmon 功率/SM**
- dmon（200ms）：慢轮窗口内 SM util 与功率的形态——若出现 SM 静默期（util 掉坑 + 功率下降）= host 侧停顿（JIT/计划/分配）⇒ 候选④；若 SM 持续高但慢 = kernel/通信效率 ⇒ 候选③。
- vLLM 侧：开 `--enable-layerwise-nvtx-tracing` + 若窗口允许重启则暴露 torch profiler（fork 未暴露 /start_profile，E1 已证）。退而求其次：用 Prometheus /metrics 的 request_queue/prefill 时间直方图按轮对齐。

**P4. 激活内存曲线（判候选①）**
- 容器内 1Hz 采样 `torch.cuda.memory_allocated/reserved`（需小脚本进 worker 进程不可行时，用 nvidia-smi/系统侧 unified memory 监控替代）+ `VLLM_DEBUG_WORKSPACE=1`（workspace.py 已有该 env，:51-58）打印 workspace 尺寸与 resize 事件。
- **预期信号**：慢轮对应 workspace resize/empty_cache 事件 ⇒ 候选①残余成立；无 ⇒ 排除。

**P5. 归因决策树**
```
慢轮存在？
├─ 否 → threshold 2048 直接 +15-18%（快轮已示），进入扩 M 到 4096 阶梯实验
└─ 是 → 慢轮与 JIT 时间戳相关？
   ├─ 是 → 扩 warmup 覆盖形状后复测；若消除 → 根因=形状 JIT，threshold 本身无罪
   └─ 否 → SM 静默期存在？
      ├─ 是 → host 侧（plan/调度/分配）profiling，钉到函数
      └─ 否 → RDMA 错误跳升？
         ├─ 是 → NCCL 拥塞/重传（考虑 NCCL_BUFFSIZE=16MB A/B）
         └─ 否 → kernel 级（profiler 必须争取重启暴露）
```

## 2. 研究二（P1）：workspace 跨层去重设计

### 2.1 关键口径修正（先修正问题本身）【实证-源码】

**生产 MoE 路径考证**：`--moe-backend flashinfer_b12x` 经 oracle 映射（`fused_moe/oracle/mxfp4.py:290` `"flashinfer_b12x": [Mxfp4MoeBackend.B12X_MXFP4]` → `:180-185`）到 **社区 b12x 包的 `B12xExperts`**（`experts/b12x_mxfp4_moe.py`，生产日志 `mxfp4.py:1734 "Using B12xExperts"` 印证）——**不是** FlashInfer wrapper 的 `FlashInferB12xExperts`（命名陷阱：CLI 名带 "flashinfer" 但走的是 b12x 包）。

因此：
- **当前生产 W4A16 无 ×43 重复**：`B12xExperts.apply()` 的 scratch 来自 vLLM 全局 `WorkspaceManager`（`modular_kernel.py:1078-1094` `_allocate_buffers` → `v1/worker/workspace.py:92-146` get_simultaneous 单例缓存，每 ubatch 一个 buffer，43 层共享，仅按需 resize）。upstream 报告 §2.A1 以"我们 P2 实测 +28GB 工作区×43 层"作为生产痛点的表述需要修正——该 +28GB 实为 **W4A4 混合路线实验**（engineering-assets E2：TTFT -13%/-47%、KV -52%、**weight +28GB**、hybrid +42GB 吃光 KV、根因"CG=1 锁定 static workspace 路径"）的发现。
- **×43 重复的真实位置**：`experts/flashinfer_b12x_moe.py` 的 `FlashInferB12xExperts`（nvfp4/W4A4 路线）——`_ensure_wrapper()`（:249-266）每层实例 lazy 创建一个 `B12xMoEWrapper(use_cuda_graph=True, max_num_tokens=4096)`，wrapper `_allocate_buffers()`（flashinfer `b12x_moe.py:385-458`）为**每层**独立分配 workspace。

### 2.2 分配点源码定位与几何同构性【实证-源码】

**FlashInfer wrapper 路径每层分配明细**（flashinfer 0.6.15 `fused_moe/cute_dsl/blackwell_sm12x/moe_dispatch.py`）：
- W4A16 量化：`Sm120W4A16MoEWorkspace`（:1886-2069）：`intermediate_cache13 = routed_rows × max(2n, k) × bf16`（生产几何 routed_rows=4096×6=24576、k=4096 ⇒ **~201MB**）、`intermediate_cache2 = 24576×512×bf16`（~25MB）、`fc1/fc2_c_tmp`（fp32 scratch）、route 缓冲（~MB 级）+ wrapper 私有 `_moe_output = 4096×4096×bf16`（~33.5MB）。
- nvfp4 量化（W4A4）：static（`Sm120StaticMoEWorkspace` :259-，含 `token_map = state_E×max_rows×int32` ≈ 25MB、`packed_input = rows×k/2` ≈ 50MB…）+ 视 cutover 加 dynamic（`Sm120DynamicMoEWorkspace` :1202-，task/tile 数组族）。每层合计 ~0.3-0.65GB——与 W4A4 实验每层实测一致。
- **同构性**：`/models/config.json`——43 层全部 `n_routed_experts=256、num_experts_per_tok=6、moe_intermediate_size=2048、hidden_size=4096`（无 first_k_dense 差异化 MoE 几何）⇒ **43 层 workspace 几何完全同构，共享一份即可**。

**共享安全性论证**【实证-源码】：
1. wrapper 对权重无状态：`run()` 每次调用传入 w1/w2（`b12x_moe.py:472-546`）；内部 `_W4A16_WEIGHT_CACHE`/`_weight_views` 缓存键含 `data_ptr()`（moe_dispatch.py:2100-2116）⇒ 跨层共享 wrapper 不会串权重。
2. workspace 为纯 scratch：写前读语义由 launch kernel 保证（packed_route_count/expert_offsets 等先写后读）；层间串行（同一 stream 顺序执行）⇒ 层 N+1 覆写层 N 残留安全。
3. CUDA graph：decode 捕获（尺寸 1-96）要求 workspace 捕获前已存在且地址稳定——wrapper 在首次 apply（profile_run/dummy_run 阶段）创建，早于捕获 ⇒ 共享池同样满足；唯一红线是共享后**禁止 resize**（锁定容量 = max_num_tokens）。

### 2.4 fork 内自做方案设计

**方案 A（推荐，对症 W4A4/FlashInfer wrapper 路径）**：在 `vllm/model_executor/layers/fused_moe/experts/flashinfer_b12x_moe.py` 增加模块级几何键 wrapper 池。

- **改动点（文件/函数级）**：
  1. `flashinfer_b12x_moe.py`：新增模块级 `_B12X_WRAPPER_POOL: dict[tuple, B12xMoEWrapper]`；`FlashInferB12xExperts._ensure_wrapper()`（:249-266）改为按几何键 `(num_experts, topk, hidden, intermediate, max_num_tokens, activation, quant_mode, source_format)` 查池，miss 时创建并注入池。
  2. 同文件 `workspace_shapes()`（:225-235）保持 `(1,),(0,)` 不变（wrapper 自管）。
  3. 生命周期：池随进程存活；worker 销毁时无需显式回收（进程退出）。加 `VLLM_B12X_SHARED_WRAPPER=0/1` env 开关便于 A/B 与回滚。
- **共享池生命周期管理**：首个使用该几何的层在首次 apply 时创建（profile_run 阶段，早于 cudagraph 捕获）；容量锁定 `max_num_tokens=4096`，之后任何 resize 需求直接报错（fail-fast，防 graph 地址漂移）；`_moe_output` 同池共享（apply() 中 `output.copy_(wrapper_output)` 立即消费，安全）。
- **风险**：①若未来引入层间并行（如 LayerOverlap/async TP），共享池需按 lane 区分——b12x 文档已预警（"Independent overlapping lanes must use distinct pools"）；②EP 启用时 num_local_experts 进入键；③需要回归验证 W4A4 数值一致性（共享后 buffer 残留理论无影响，但要有 golden 测试）。
- **工作量**：补丁 ~60 行 + env 开关 + 单测/回归，**2-4 天**（含 W4A4 复测）；预期收益 = W4A4 路线 workspace 43×→1×（~13-27GB），解除 "+42GB 吃光 KV" 的结构性封锁——**这是重启 W4A4/W4A8 路线的前置条件**，与 pr-de 报告"W4A4 仅当扩 M 落地后再评估"的结论正交。

**方案 B（可选，生产 W4A16 路径的稳健化）**：把 fork 桥接层 `b12x_mxfp4_moe.py` 的每调用 `_plan_b12x_moe_fp4_scratch()` 改为常驻 `TPMoEWorkspacePool` + `bind_shared_arena()`（b12x 0.15.3 现成 API）。
- 收益：生产路径的 plan/bind host 开销常驻化（每步 43 次纯 host 规划 → 池查表）、route arena 固定化（顺带吸收 #226 的尾块特化收益，对研究一候选④有对冲作用）。
- 风险：与 vLLM WorkspaceManager 的双缓冲所有权需要理清（scratch 仍可从 workspace2 切到 pool 的 shared_arena）；工作量 **1-2 周**。优先级低于方案 A。

### 2.5 原型补丁伪代码（附录，供实施代理）

```python
# === vllm/model_executor/layers/fused_moe/experts/flashinfer_b12x_moe.py ===
# 方案 A 原型：跨层共享 B12xMoEWrapper（几何键池）

import vllm.envs as envs

_B12X_WRAPPER_POOL: dict[tuple, Any] = {}   # geometry key -> B12xMoEWrapper
_POOL_LOCK = threading.Lock()

def _b12x_wrapper_pool_enabled() -> bool:
    return bool(int(os.getenv("VLLM_B12X_SHARED_WRAPPER", "1")))

class FlashInferB12xExperts(mk.FusedMoEExpertsModular):
    ...
    def _ensure_wrapper(self) -> None:
        """Lazily create *or fetch* B12xMoEWrapper.

        43 层 MoE 几何同构（E=256, topk=6, k=4096, n=512/rank），且 wrapper
        对权重无状态（run() 每调用传参、内部缓存键含 data_ptr），
        因此全部层共享一个 wrapper 实例是安全的 —— workspace 43x -> 1x。
        """
        if self._wrapper is not None:
            return

        from flashinfer.fused_moe import B12xMoEWrapper

        if not _b12x_wrapper_pool_enabled():
            self._wrapper = B12xMoEWrapper(          # 原行为（回滚臂）
                num_experts=self.global_num_experts,
                top_k=self.topk,
                hidden_size=self.hidden_dim,
                intermediate_size=self.intermediate_size_per_partition,
                use_cuda_graph=True,
                max_num_tokens=self.max_num_tokens,
                num_local_experts=self.num_local_experts,
                activation=self._activation_str,
            )
            return

        # 几何键：任何影响 workspace 形状的参数都进键
        key = (
            self.global_num_experts, self.topk,
            self.hidden_dim, self.intermediate_size_per_partition,
            self.max_num_tokens, self.num_local_experts,
            self._activation_str,          # quant_mode 固定 nvfp4（本类只支持 nvfp4）
        )
        with _POOL_LOCK:
            wrapper = _B12X_WRAPPER_POOL.get(key)
            if wrapper is None:
                wrapper = B12xMoEWrapper(
                    num_experts=self.global_num_experts,
                    top_k=self.topk,
                    hidden_size=self.hidden_dim,
                    intermediate_size=self.intermediate_size_per_partition,
                    use_cuda_graph=True,          # 容量锁定，禁止后续 resize
                    max_num_tokens=self.max_num_tokens,
                    num_local_experts=self.num_local_experts,
                    activation=self._activation_str,
                )
                _B12X_WRAPPER_POOL[key] = wrapper
                logger.info(
                    "B12x shared wrapper pool: created wrapper for geometry %s "
                    "(pool size=%d; per-layer workspace dedup active)",
                    key, len(_B12X_WRAPPER_POOL),
                )
        self._wrapper = wrapper

    # apply() 不变：权重每调用传入，data_ptr 键控的内部缓存天然分层。
    # 验证要点（实施代理 checklist）:
    #  1) 启动日志确认 pool size == 不同几何数（当前模型应 = 1，MTP 层若几何不同则 2）
    #  2) 显存前/后对比：nvidia-smi / torch.cuda.memory_reserved 应减 ~ (43-1)×每层 workspace
    #  3) W4A4 数值回归：golden 输出逐 token 对比（共享前后必须 bit-exact——scratch 写前读）
    #  4) cudagraph 捕获正常（decode 尺寸 1-96）+ 首个 prefill 请求无 workspace 相关报错
    #  5) A/B：VLLM_B12X_SHARED_WRAPPER=0/1 各跑 PR 四档 + DE C1/C12，确认吞吐无回归
```

**组件级评估**：

- **WO/MHC/FP8 GEMM**：fork 有自有实现（TileLang MHC、o_proj），替换 = 在自定义模型类里改装配点——中等工程，且收益未知（MHC 已有自有优化）。

**建议路线（按序）**：
1. **不动生产 fork**（当前自定义栈是已知稳定基线，且 attention 非头号瓶颈）。
2. **窗口期用 Eugr 镜像做并行 A/B**（零 fork 改动，4 节点可跑 TP4：镜像+配方现成，测 PR/DE 四档+正确性）——这是评估"整体栈是否值得"的最廉价路径；同时验证 b12x MoE stall 是否复现于 4 节点 TP4。
3. 若 A/B 显示显著优势 → 走 upstream 报告路径 3（fork 的 DSV4 自定义类移植到 main + B12X 全家桶），把 attention/WO/MHC/FP8 一并吸收；若优势不显著或 stall 复现 → 维持现状，仅收割研究二/三的低风险项。
4. 无论走哪条路，`VLLM_USE_BREAKABLE_CUDAGRAPH` 的社区警示（breakable 在 GB10 伤 prefill）值得在我们环境单独 A/B——我们生产开着 =1 而社区配方关掉，这是一个**零成本可验证的现成差异点**。
