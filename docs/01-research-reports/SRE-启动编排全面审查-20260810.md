### 1.5 死循环修复有效性判定：**有效**
dockerd journal 铁证（boot 窗口）：
```
23:18:52 dockerd: Loading containers: start. / Restoring containers: start.

- 旧容器在本次 boot 的 23:18:55 被 docker 自动恢复（这正是事故原型的直接证据）；编排幂等清理将其 SIGKILL；新容器带 `--restart no`。
- 由于 head/worker 现在都是 `--restart no`，**docker 在 daemon 重启/崩溃后不会再自动拉起 vLLM 容器**，死亡循环在机制上被堵死。

### 1.6 本次崩溃根因：NVRM 驱动级 NV_ERR_NO_MEMORY
```
dmesg:
[  238.920359] NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory [NV_ERR_NO_MEMORY] (0x00000051)
              returned from _memdescAllocInternal(pMemDesc) @ mem_desc.c:1359      # 首次 head(23:18:59 实例)
[ 1076.899819] ... 同上 ...                                                        # 本次 head(23:33:08 实例) 连续6条
```
- 两次 head 引擎 init（同一 boot 内）均因驱动大内存分配失败而崩溃。
- 宿主 RAM 充足（121Gi 总 / 116Gi available），**不是宿主 OOM**；`nvidia-smi` 显示 GPU 正常、Persistence=On、无进程、无 Xid。
- 最小分配测试（torch.randn(1024,1024)）**成功** → 驱动未被基本层面毒化；失败只发生在 vLLM 引擎 init 的大规模分配。
- **GPU-gate（nvidia-smi -L）无法捕获该问题**：探测通过（第 1 次即通过），引擎 init 仍失败。

## 4. vllm-cluster.service 依赖链审查

```
[Unit]
After=docker.service network-online.target nvidia-persistenced.service
Wants=network-online.target
StartLimitBurst=3
StartLimitIntervalSec=300
[Service]
Type=oneshot
User=<USER>
ExecStart=<INSTALL_DIR>/scripts/start_v026r_cluster.sh
RemainAfterExit=yes
TimeoutStartSec=1500        # 25 min
Restart=on-failure
RestartSec=60
[Install]
WantedBy=multi-user.target
```

### 4.1 After/Wants/Requires 完整性
- `After=docker.service network-online.target nvidia-persistenced.service` 合理；`Before=` 反向依赖由 docker.service 和 nvidia-persistenced 各自声明（均已确认）。
- **缺失项（低危）**：未 `After=nv-docker-gpus.service`（NVIDIA 容器运行时配置）。实测该服务在 basic.target 附近完成，docker 起来后 GPU 运行时可正常注入；建议显式补齐以消除竞态窗口。

### 4.2 TimeoutStartSec=1500 vs GPU-gate 180s
- GPU-gate 最多 180s，远超 TimeoutStartSec 预留，**匹配 OK**。
- **但**：worker 叶子脚本内部轮询上限 **30min**，加上编排 step4 再轮询 **10min**，最坏路径可达 **~40min > 1500s**。慢冷启动（>25min）时 systemd 会在编排成功前 SIGTERM，并被判定为失败触发 Restart → 误杀正常启动。**（P1，见建议）**

### 4.3 Restart=on-failure + StartLimitBurst=3/300s 评估
- 每次失败路径耗时长（step3 阻塞 30min / step4 10min / 超时 25min），**3 次/300s 的限频窗口在时间上永远达不到** → StartLimit 形同虚设。
- `Restart=on-failure` 对 oneshot 超时视为失败会重启 → 在 head 反复初始化失败场景下，编排会**无限慢循环**（每 ~30-40min 一轮），不会真正收敛到人工干预。
- **建议**：a) 增加失败后自动止损策略（如失败 N 次后 `systemctl stop` 或进入 degraded 并告警）；b) 明确「哪些失败允许自动重试、哪些应停止」；c) 若保留重试，StartLimitIntervalSec 需放大到覆盖实际失败周期，并配合告警。（P1）

## 5. 编排脚本全流程审查

### 5.1 start_v026r_cluster.sh（主编排）
步骤：前置检查 → GPU-gate(180s) → 双脚本自检 → 清理残留 → 8001 释放验证(B6) → step1 head 后台启动 → step2 轮询 TCPStore:25000 → step3 ssh 启动 worker → step4 轮询 /health+/v1/models。

问题清单：
1. **[P1] GPU-gate 深度不足**：仅 `nvidia-smi -L`（列出 GPU）。本次事故探测通过但引擎 init 因 NVRM 大分配失败。建议补充：a) `nvidia-persistenced` active 校验；b) 驱动健康探测（`nvidia-smi -q` 关键字段 / `nvidia-smi -pm 1`）；c) 最小 CUDA 分配自检（`python -c "import torch;torch.cuda.init()"` 或 vllm 镜像内小分配）；d) 探测到 NVRM/NV_ERR 模式时直接中止并给出「需重启/重置 GPU」提示。
2. **[P2] TCPStore 就绪判定过弱**：`nc -z` 端口通 ≠ 引擎就绪；且 head 可能在 TCPStore 起来后崩溃（本次正是）。当前设计是「TCPStore 通 → 启动 worker」，在 head 引擎崩溃时会把 worker 拉进必死的 Broken-pipe 死局。建议增强：step2 同时校验 head 容器存活 + head 日志无 EngineCore-fail 标记；或把「TCPStore 通 + head 容器存活 + 无失败标记」作为启动 worker 前置。
3. **[P1] head 叶子脚本失败不可见**：`nohup start_head_v026r.sh &` 后台运行，编排不检查其退出码。head 崩溃（4min 后）编排毫无感知，直到 step3 被 worker 阻塞 30min 才超时。建议：a) 后台脚本退出码写入状态文件，step2/step3 轮询时检查；b) head 叶子脚本在容器退出时立即写失败标记。
4. **[P2] 清理消息与实际不符**：清理只查 `docker ps`（running），exited 容器不触发提示；实际由叶子脚本 `docker rm -f` 兜底，功能无碍，但日志误导。建议统一用 `docker ps -a` 判定。
5. **[P2] ERR_PATTERNS 覆盖不足**：缺 `ncclSystemError|DistStoreError|NV_ERR|NVRM|Broken pipe|HeartbeatMonitor`。建议补齐以覆盖本次与历史事故模式。
6. **[P2] 挂载源检查仅 head 侧**：worker 挂载源（nvcc_wrapper/models）未在编排侧校验（叶子自检有部分覆盖），建议显式加。
7. **[P3] MAX_WAIT_S=600 与叶子 30min 不一致**：step2/step4 各 10min，但 worker 叶子 30min；总超时与 service TimeoutStartSec 存在错配（见 §4.2）。

### 5.2 start_head_v026r.sh
- 关键项：`--restart no`（已生效）；`docker rm -f` 兜底清理；`--health-cmd "pgrep -f VLLM::EngineCore"`；日志轮询 `Application startup complete`（180×10s=30min 上限）。
- 问题：
  1. **[P1] 健康检查盲区**：`pgrep EngineCore` 只证明进程存在，无法识别「进程活着但 NCCL/TCPStore 断开」的挂死（02 worker 现状）。建议健康检查增强为实际请求/心跳（如对 8001 /health 探测）或结合 worker 日志 Broken pipe 计数。
  2. **[P2] 就绪轮询只看日志关键字**：head 侧等 `Application startup complete`；若容器已退出，轮询仍空转 30min 才失败。建议检测容器状态，退出立即失败并写标记。
  3. **[P3] `docker rm -f` 对运行中容器的 SIGKILL 风险**：运行期对持有大 GPU 分配的容器直接 SIGKILL，可能在 GB10 上留下驱动内存泄漏（见 §7/§9）。建议流程改为 `docker stop -t <sec>` 优雅退出兜底 `rm -f`。

### 5.3 start_worker_v026r.sh
- 关键项：`--restart no`；`docker rm -f` 兜底；就绪判定=worker EngineCore 存活 + head /health=200（30min）。
- 问题：
  1. **[P1] 无 head 死亡快速失败**：head 崩溃后 worker 叶子仍空转轮询到 30min，导致编排 step3 阻塞 30min。建议：head /health 连续 N 次 000 且 worker EngineCore 仍存活 → 判定 head 已死，立即退出并携带失败码。
  2. **[P2] `docker exec pgrep` 依赖容器内 pgrep**：建议兼容性检查或改用 `docker inspect` 状态 + 日志特征。
  3. **[P3] 与 head 相同的 SIGKILL 清理风险**（见 head）。

### 5.4 check_vllm_script.sh
- 覆盖语法/续行/尾随空格/关键参数/依赖文件/SERVE_CMD 长度/HOME 检查，**质量良好**。
- 建议补充：关键参数检查为「必备项」，但缺 `--restart no` 校验（防回归）；可加 NVRM/NV_ERR 相关告警。

## 6. boot 时序推演

### 6.1 正常路径
```
开机 (23:18:44)
├─ systemd 启动 NVIDIA 驱动 (NVRM 9.96s / modeset 9.98s, 580.173.02)
├─ nvidia-persistenced (active, Before=vllm-cluster)
├─ docker.service @3.8s +2.5s（恢复 unless-stopped 监控容器）
├─ network-online.target（NetworkManager @1.65s）
└─ vllm-cluster.service（After docker+network+persistenced）
   ├─ GPU-gate(nvidia-smi -L ≤180s) → 脚本自检 → 清理残留 → 8001 校验
   ├─ step1 head(docker run --restart no) → TCPStore:25000
   ├─ step2 轮询 TCPStore(≤600s)
   ├─ step3 ssh 02 → worker(docker run --restart no) → 30min 就绪轮询

### 6.2 剩余竞态与脆弱点
1. **[P0] 驱动大分配不稳定（NVRM NV_ERR_NO_MEMORY）**：本次 boot 后两次引擎 init 均失败；`nvidia-smi -L`/小分配正常但大分配失败。当前**无自动恢复路径**——head 容器 `--restart no` 不会自愈，编排只是反复失败重试。

5. **[P2] 大分配测试/强制 kill 的泄漏风险**：对运行中 vLLM 容器 `rm -f`/OOM-kill 可能在共享内存 GB10 上遗留驱动内存，需优雅退出与 GPU 重置策略。

### R3.3 根因判断
1. **不是本集群配置固有缺陷**：同配置（`--gpu-memory-utilization 0.80`、max-model-len 768000）在干净 boot 后成功加载 155.43 GiB 权重（48 shards）、完成 CUDA graph capture、并服务真实推理。
2. **不是宿主 OOM**：MemTotal 121.6 GiB；失败时 MemAvailable 仍有 36–42 GiB；无 OOM-kill。
3. **是 GB10 统一内存架构下驱动内部 mem_desc 分配的慢性脆弱点**：`_memdescAllocInternal @ mem_desc.c:1359` 是驱动为 GPU 对象分配内部内存描述符的路径，失败发生在 CUDA OOM 暴露之前。社区（NVIDIA 论坛多帖、双 DGX Spark 部署者）确认同签名，定性为 **UMA-structural**（统一内存压力/碎片积累 → 驱动内部分配失败），onset 随会话内累计分配/运行时长上升，多数场景仅 reboot 可恢复。
4. **上轮（08-10 晚）致命化的触发链**：先有崩溃/SIGKILL/96GiB 压力测试留下的驱动内存碎片与占用 → 驱动大分配在压力下从"transient 可吸收"恶化为"致命" → head 引擎 init 连续两次失败 → 节点 SSH 不可用。**本次重启清空驱动状态后同配置成功**，与该判断一致。
5. 内存预算：0.80 × 121.6 ≈ 97.3 GiB GPU 预算；权重 ~77.7 GiB/节点（TP2 均分）；KV+激活+graph 余量 ~19.6 GiB；运行期实际 used ~107 GiB / available ~14 GiB → **余量偏紧**，并发大请求时碎片风险上升。

### P3.3 为何 580.178.04 不可安全安装（关键证据）
1. `/etc/apt/preferences.d/cuda-compute-repo-lowpri2` 将 `nvidia-*580`/`libnvidia-*580`（CUDA 源）**pin 为 -1**——DGX OS 主动禁用该路径，`apt-cache policy` 显示候选仍为已装 580.173.02，`apt-get -s install` 无动作。
2. CUDA 源 580.178.04 的 `Depends: nvidia-dkms-580-open (= 580.178.04-1ubuntu1)`。**DGX OS 官方规范不用 DKMS**（NVIDIA 论坛明确 "DKMS is not part of DGX OS. The nvidia driver is packaged as a .deb"），2026-03~05 多名 DGX Spark 用户因 nvidia-dkms-580-open 在 secure boot 下 DKMS 编译失败/半配置状态（iU）而驱动失效。
3. 无 `linux-modules-nvidia-580-open-6.17.0-1029-nvidia` 的 580.178.04 配套预编译模块（当前仅 6.17.0-1029.29+1/580.173.02）。强行安装会造成 userspace(580.178.04) 与内核模块(580.173.02) 不匹配或走 DKMS 风险路径。
