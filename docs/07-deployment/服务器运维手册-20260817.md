## 1. 概述

### 1.1 环境拓扑（四机角色 / 环网 / TP4）

生产为 4× NVIDIA DGX Spark（GB10，UMA 121.6GiB，20 核异构）**纯环网** Tensor Parallel=4（vLLM）。环序 **01(rank0)→02(rank1)→04(rank2)→03(rank3)→01**。

| rank | 主机 | 管理网（2.5GbE） | RoCE 环邻（每边双链路） | systemd 单元 | 节点角色 |
|---|---|---|---|---|---|
| 0 | node01 | <NODE_IP> | 02(f1) / 03(f0)：<RING_SUBNET>、<RING_SUBNET> | `vllm-tp4-head.service` | **head** + 数据源（3.6T） |
| 1 | node01 | <NODE_IP> | 01(f1) / 04(f0)：<RING_SUBNET>、<NODE_IP>/30+<NODE_IP>/30 | `vllm-tp4-worker.service` | worker + 监控 + registry + 数据源（3.6T） |
| 2 | node01 | <NODE_IP> | 02(f0) / 03(f1)：10.20.0.x、<RING_SUBNET> | `vllm-tp4-worker.service` | worker + embed（916G） |
| 3 | node01 | <NODE_IP> | 04(f1) / 01(f0)：<RING_SUBNET>、<RING_SUBNET> | `vllm-tp4-worker.service` | worker + embed（916G） |

> 注：rank 与主机名映射为 **01=0、02=1、04=2、03=3**（03/04 对调，以 systemd NODE_RANK 实测为准，勿按主机号顺推）。

**网络关键参数（四机）**：
- 管理网 <NODE_IP>~<NODE_IP>（2.5GbE，控制面/SSH/API/监控）

- QoS：DSCP trust + PFC（`NCCL_IB_TOS=46`）

### 1.2 服务架构（systemd + monitor + docker 三层）

```
systemd 单元（vllm-tp4-head.service @01 / vllm-tp4-worker.service @02/03/04，Restart=always）
   └─ ExecStart ─ monitor_tp4_head.sh / monitor_tp4_worker.sh（自愈 monitor，恒非零退出）
        ├─ 容器在 → docker wait（跟随退出）→ exit 1 → systemd Restart=15s
        ├─ 容器不在(head) → ssh 清 worker → start_tp4_head.sh → TCPStore 就绪门禁(≤60s) → 等 3 worker 接入
        └─ 容器不在(worker) → head API=200 且集群成形？→ 互杀守卫触发 head 全链重建；
             否则等 head TCPStore:25999(≤120s) → start_tp4_worker.sh（含 D1 模型就绪门禁，exit2 指数退避）
   └─ 容器（vllm-tp4-rank0~3，--restart no，生命周期由 systemd 掌控）
        └─ 进程级探针（healthcheck.timer @01，60s）→ healthcheck-rebuild.sh → docker rm -f → 全链重建
```

- **head 单点**：`vllm-tp4-rank0`（01，host 网络，:8001）
- **workers**：`vllm-tp4-rank1`(02)、`vllm-tp4-rank2`(04)、`vllm-tp4-rank3`(03)
- 容器 `--restart no` 为**有意设计**：TP4 分布式集群单容器自行拉起会造成 split-brain/rank 不一致，协调式重建（head-first）更正确；生命周期完全由 systemd 掌控。
- 前置依赖：unit 已含 `Wants=... docker.service` + `After=... docker.service`（P1-① 生效）。
- 关键 systemd 参数（四机一致）：`Restart=always` / `RestartSec=15` / `StartLimitIntervalSec=1800` / `StartLimitBurst=20` / `TimeoutStartSec=1500` / `User=<USER>` / `EnvironmentFile=<INSTALL_DIR>/secrets/vllm.env`（600 root:root）。

## 2. 启停操作

> **sudo 说明**：本文命令中 `sudo` 前缀标注为**需要 root 的操作**（systemctl stop/start、logrotate、journald 等）。本环境以 <USER> 运维账号 SSH 登录，sudo 需交互输入密码（未配置 NOPASSWD）；已在 sudoers 白名单中的操作可 `sudo -n` 免密执行。每个命令均给出**可直接复制执行**的完整形式，`<...>` 为需替换占位符。

### 2.1 日常状态检查

```bash
# ① 服务活性（head 01）
ssh node01 'systemctl is-active vllm-tp4-head.service; systemctl is-active vllm-tp4-worker.service'
# 期望：head=active；worker=inactive（01 正确）

# ② worker 活性（02/03/04，各机 worker=active）
for h in node01 node01 node01; do
  echo "== $h =="; ssh $h 'systemctl is-active vllm-tp4-worker.service; docker ps --format "{{.Names}}\t{{.Status}}" | grep vllm-tp4'
done

# ③ 容器状态（四机，期望 rank0~3 全 Up(healthy)）
for h in node01 node01 node01 node01; do
  echo "== $h =="; ssh $h "docker ps --format '{{.Names}}\t{{.Status}}' | grep vllm-tp4"
done

# ④ API 健康（/health 免鉴权）
curl -s -o /dev/null -w 'health=%{http_code}\n' http://<NODE_IP>:8001/health    # 期望 200

# ⑤ 模型与鉴权（/v1/models 需 Bearer；密钥从 secrets/vllm.env 取，勿明文落命令行）
ssh node01 'sudo -n cat <INSTALL_DIR>/secrets/vllm.env 2>/dev/null | grep -q VLLM_API_KEY && \
  export $(sudo -n cat <INSTALL_DIR>/secrets/vllm.env | xargs) && \
  curl -s -H "Authorization: Bearer ${VLLM_API_KEY}" http://<NODE_IP>:8001/v1/models | head -c 300'
# 期望：返回 deepseek-v4-flash-0731，max_model_len=400000

# ⑥ metrics（免鉴权；running/waiting 应为 0/0）
curl -s http://<NODE_IP>:8001/metrics | grep -E "^vllm:(num_requests_running|num_requests_waiting) "

# ⑦ 生产库 md5 抽查（四机必须一致）
for h in node01 node01 node01 node01; do
  echo "== $h =="; ssh $h 'md5sum /opt/nccl-ringonly/libnccl.so.2.30.7 <INSTALL_DIR>/lib/libncclpin.so'
done
# 期望：2be94172c1172734d00dee9ff7d788bd / ce43c688c5164ac7efd5105c94fdab77

# ⑧ 关键日志无错误
ssh node01 'journalctl -u vllm-tp4-head.service -n 50 --no-pager | grep -iE "error|110|traceback" | grep -v "0 errors" || echo "NO_ERRORS"'
ssh node01 'docker logs vllm-tp4-rank0 --tail 200 2>&1 | grep -iE "NCCL version|error" | tail -5'
```

**巡检结果判读**：`systemctl is-active` 非 active / 容器非 healthy / health 非 200 / md5 不一致 → 进入 §2.5 故障应急。

### 2.2 单机服务重启（worker / head 分别）

**原则**：① 先 `systemctl stop`（防 monitor 自动重建），等 15-30s 再操作容器；② 停 worker 先、head 最后；③ 正常恢复用 systemd 启，**不要 docker start 单容器**（TP4 需协调式重建）。

```bash
# ── 重启单个 worker（以 02/rank1 为例）──
ssh node01 'sudo systemctl stop vllm-tp4-worker.service'
ssh node01 'sleep 20; docker ps -a --filter name=vllm-tp4-rank1 --format "{{.Names}} {{.Status}}"'   # 确认容器退出
ssh node01 'sudo systemctl start vllm-tp4-worker.service'
# 观察：monitor 会等待 head TCPStore(≤120s) → 重建 rank1 容器 → 若集群已成形且 rank1 缺失，可能触发 head 全链重建（正常）

# ── 重启 head（01）──
ssh node01 'sudo systemctl stop vllm-tp4-head.service'
ssh node01 'sleep 20; docker ps -a --filter name=vllm-tp4-rank0 --format "{{.Names}} {{.Status}}"'
ssh node01 'sudo systemctl start vllm-tp4-head.service'
# head monitor 重建流程：先 ssh 清 02/04/03 worker 容器 → 新 head 容器 → TCPStore 就绪 → 等 3 worker 接入
# 模型冷加载 ~155GiB，完整收敛约 5-7min（实测 head 重启至 healthy ≈ 5.2min）
```

> **注意**：head 重启会**主动清空三个 worker 容器**（head-first 全链重建），单机 head 重启≠只影响 head。

### 2.3 四机整停 / 整启顺序

**停机顺序（维护窗口）**：worker 先停（03→04→02）→ head 最后（01）。反向启机：head 先（01）→ worker（02→04→03）。

```bash
# ══════ 四机整停（标准维护窗口）══════
# ① 停 worker（先 03→04→02）
ssh node01 'sudo systemctl stop vllm-tp4-worker.service'
ssh node01 'sudo systemctl stop vllm-tp4-worker.service'
ssh node01 'sudo systemctl stop vllm-tp4-worker.service'
# ② 停 head（最后）
ssh node01 'sudo systemctl stop vllm-tp4-head.service'
# ③ 确认 monitor 已退出、无残留容器（防自愈残留进程占用 GPU）
for h in node01 node01 node01 node01; do
  echo "== $h =="
  ssh $h "docker ps -a --filter name=vllm-tp4-rank --format '{{.Names}} {{.Status}}'; \
    systemctl is-active vllm-tp4-head.service vllm-tp4-worker.service"
done
# 期望：无容器输出；systemd 全 inactive/failed
# 残留处置（确认 monitor 已停才可执行）：docker rm -f vllm-tp4-rank0~3

# ══════ 四机整启（标准流程）══════
# 方案 A：编排入口（01，head-first 幂等，推荐）
ssh node01 'cd <INSTALL_DIR>/scripts && bash start_tp4_cluster.sh'
# 方案 B：手工 systemd 顺序（01 head 先 → 02/04/03 worker）
ssh node01 'sudo systemctl start vllm-tp4-head.service'
sleep 30
for h in node01 node01 node01; do
  ssh $h 'sudo systemctl start vllm-tp4-worker.service'
  sleep 10
done
```

**整启注意事项**：
1. 开机顺序 01→02→03→04；systemd 已 enable，**正常重启勿手动启**（head monitor 会自动拉起 head + 清 worker 链式自愈）。
2. 前置校验（重启后必查）：`isolcpus=8-9`（nproc=18）/ RoCE MTU 9000 / GID=3 / `/opt/nccl-ringonly` md5 `2be94172` / shim v8 md5 `ce43c688`。
3. 内存余量：01/02 若 <10G 余量先清 buff/cache（`sudo sync && echo 3 | sudo tee /proc/sys/vm/drop_caches`，生产谨慎执行）。
4. **互杀守卫**：冷启动未成形时 worker 不会杀 head（防冷启动互杀）；集群成形后单 rank 缺失会触发全链重建（宁重建不留半集群，正确性优先）。

### 2.4 完整重启流程（含模型加载等待与健康确认清单）

以"四机整机重启"为例（实测 01 reboot → healthy ≈ **7min11s**；worker→head 滚动重启）：

```bash
# ── 前置：重启前确认基线 ──
ssh node01 'cat /proc/cmdline | tr " " "\n" | grep isolcpus'          # isolcpus=8-9
ssh node01 'ip link show | grep -A1 "mtu" | grep -E "mtu 9000" | head' # RoCE MTU 9000
# ── 执行滚动重启：worker 03→04→02→head 01，每机间隔等 SSH 恢复 ──
ssh node01 'sudo reboot'
# …等待 ssh 恢复后继续 04、02、01 …
ssh node01 'sudo reboot'
ssh node01 'sudo reboot'
ssh node01 'sudo reboot'     # head 最后，触发 head-first 全链重建
# ── 等待与收敛确认（head 重启后）──
# 模型加载 ~155GiB 冷加载（TimeoutStartSec=1500=25min 兜底；实际 <10min）
for i in $(seq 1 30); do
  code=$(curl -s -m 5 -o /dev/null -w '%{http_code}' http://<NODE_IP>:8001/health 2>/dev/null || echo 000)
  echo "[$i] health=$code"
  [ "$code" = "200" ] && break
  sleep 30
done
```

### 2.5 故障应急（按场景）

| # | 场景 | 现象 | 处置 | 恢复机制 / 时长 |
|---|---|---|---|---|
| 1 | **进程崩溃（容器退出）** | rank 容器 Exited，systemd 自动 Restart | **勿人工插手**，观察 5 分钟；`journalctl -u vllm-tp4-*` 定位 | monitor `docker wait` 感知 → exit 1 → systemd Restart=15s → 重建该 rank；worker 缺失且集群成形 → 互杀守卫触发 head 全链重建。**实测 ~5min11s** |
| 2 | **容器挂（hang/无响应）** | 容器 Up 但无响应、docker wait 未返回 | `docker kill vllm-tp4-rank{N}`（用宿主机 docker kill，**容器内 kill -9 1 无效**，pid1 受 PID namespace 保护）→ monitor 感知退出 → systemd 重建 | 同场景 1；若 head 被 kill → head-first 全链重建 |
| 3 | **API 挂（EngineCore 死锁，容器仍 Up）** | `/health` 000 但 `docker ps` 显示 healthy（HEALTHCHECK 只查进程） | **自动**：01 的 `vllm-healthcheck.timer`(60s) 探针失败 → `healthcheck-rebuild.sh` → `docker rm -f rank0` → 全链重建；**手动兜底**：`ssh node01 'bash <INSTALL_DIR>/scripts/healthcheck-rebuild.sh --role head --cooldown 1800'` | 触发后 ~5min12s；探针窗口 ~2.5min（60s 周期+判定） |
| 4 | **整机宕机** | 单机 reboot / 掉电 | 等 SSH 恢复后系统自动拉起（unit 已 enable）；**开机顺序 01→02→03→04** 依赖运维编排；若 head 先于 worker 恢复则 head monitor 自动全链重建 | head reboot → healthy ≈ 7min11s |
| 5 | **8001 全挂（P0）** | `/health` 000、四机状态异常 | 立即联系 Rex/oncall；先判级再动手，走 §2.4 重建；不要盲目 `docker start` | systemd 自愈优先；人工介入走 §2.3/§2.4 |
| 6 | **模型/NFS 未就绪** | worker 退避循环（exit 2） | worker monitor 自动指数退避（60s×n，≤10 次）；检查 `<INSTALL_DIR>/models/deepseek-v4-flash-0731/config.json` 可读 | D1 门禁（≤300s）+ 退避自动恢复 |
| 7 | **网络抖动** | NCCL 超时/断连 | `--distributed-timeout-seconds 300` 兜底；monitor 内 ssh/curl 失败均 `\|\| true` 容忍 + 退避 | 自动重连/重建 |

**故障定位三步**：
```bash
# ① 判级
curl -s -o /dev/null -w '%{http_code}\n' http://<NODE_IP>:8001/health   # 000=P0 全挂 / 200=单点问题
# ② 读日志（依次）
ssh node01 'journalctl -u vllm-tp4-head.service -n 100 --no-pager'
```

### 4.1 bench_v2.py（vLLM v2 基准体系）

位置：`<INSTALL_DIR>/bench_v2.py`（md5 `56ad5ef2...`）
用途：DE 文本吞吐 / PR 纯 prefill / 接受率 / dspark / monitor 采样。输出到 `verification-logs/BENCHV2_<ts>/<group>/`。

**VLLM_API_KEY 用法（推荐，避免 key 落命令行/ps/日志）**：
```bash
# ① 从 secrets/vllm.env 读取密钥注入环境（生产实操）
ssh node01 'export $(sudo -n cat <INSTALL_DIR>/secrets/vllm.env | xargs) && \
  python3 <INSTALL_DIR>/bench_v2.py \
    --endpoint http://<NODE_IP>:8001/v1 \
    --model deepseek-v4-flash-0731 \
    --run-type pr --prefix-len 32768 --concurrency 1 --rounds 3 \
    --group MY_SPOTCHECK'
# ② 或显式 --key（慎用：会进 shell 历史/ps；优先 env）
# python3 <INSTALL_DIR>/bench_v2.py --endpoint http://<NODE_IP>:8001/v1 --key "<VLLM_API_KEY>" ...
```
> 脚本默认 `--key` 取 `VLLM_API_KEY` 环境变量；显式 `--key` 优先。未提供 key 时脚本报 `[fatal] 未提供 API key`。

**参数表**：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--endpoint` | 必填 | vLLM /v1 地址，如 `http://<NODE_IP>:8001/v1` |
| `--key` | `VLLM_API_KEY` env | API key（env 优先推荐） |
| `--model` | - | served-model-name |
| `--group` | - | 结果组名（目录名） |
| `--run-type` | - | `de` / `pr` / `both` |
| `--concurrency` | - | 并发数（可多值） |
| `--task-type` | - | coding / json / prose |
| `--input-len` | 512 | DE 输入 token 目标 |
| `--output-len` | 4096 | DE 输出 max_tokens |
| `--prefix-len` | - | PR 前缀 token 目标 |
| `--rounds` | - | 每档波数 |
| `--random-seed` | - | 随机前缀基础 seed |
| `--no-ignore-eos` | - | 关闭 DE 强制满长（默认开） |
| `--base-dir` / `--out` | - | 输出目录（`--out` 显式覆盖默认） |
| `--cooldown` | - | 档间冷却秒数 |
| `--request-timeout` | - | 单请求总超时 |
| `--monitor-interval` / `--metrics-url` / `--no-monitor` | - | monitor 采样控制 |
| `--precheck` / `--precheck-hosts` | - | 批次前预检（running==0/dspark 起始/四机健康） |

## 5. 安全与维护

### 5.1 密码脱敏原则

- **明文密码/API key 一律不入文档、不入仓库、不入命令行**。
- 文档中密钥一律脱敏显示，如 sudo 密码记作 `AS12******`（仅保留前缀长度提示，不写完整）。
- 生产脚本通过 `EnvironmentFile=<INSTALL_DIR>/secrets/vllm.env`（600 root:root）注入密钥，systemd 以 root 读取后降权运行。
- 敏感文件权限基线：`<INSTALL_DIR>/secrets/vllm.env` = `-rw------- root root`（600）。
- 已知风险（P1-4）：API key 明文会出现在 `journalctl` 的 serve 命令日志中（既有行为），评估日志脱敏为待办。

### 5.2 API key 管理（env 注入）

| 使用方 | 方式 | 说明 |
|---|---|---|
| vLLM 服务 | `--api-key "${VLLM_API_KEY}"`，由 systemd EnvironmentFile 注入 | 容器内环境变量，不落脚本明文 |
| bench_v2.py | `VLLM_API_KEY` 环境变量（或 `--key`） | 优先 env，避免 key 落 ps/日志 |
| bench_prefill_decode_async.py | `--key` 必填（无 env 默认） | 传 env 展开，勿写死 |
| curl 手测 | `Authorization: Bearer $VLLM_API_KEY` | 从 secrets/vllm.env 读取后展开 |

```bash
# 正确读 key 方式（不留痕）
ssh node01 'export $(sudo -n cat <INSTALL_DIR>/secrets/vllm.env | xargs); \
  curl -s -H "Authorization: Bearer ${VLLM_API_KEY}" http://<NODE_IP>:8001/v1/models | head -c 300'
```

### 5.3 日志轮转策略

| 日志 | 策略 | 上限 |
|---|---|---|
| vLLM 容器日志 | docker `--log-opt max-size=100m --log-opt max-file=5` | ≤500MB/容器 |
| 其他容器（aicad-* 等） | logrotate `/etc/logrotate.d/vllm-tp4`（size 100M/daily/rotate 5/copytruncate） | ≤~600MB/容器 |

| journald | `SystemMaxUse=500M` drop-in（四机） | ≤500M/机 |
| maintenance.log | 追加写入（clean_tmp_logs 自管） | 小 |
