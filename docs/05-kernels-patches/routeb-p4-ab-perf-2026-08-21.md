## 0. 核心结论（先读）

| 判据（precheck） | 结果 | 判定 |
|---|---|---|
| routeB ≥ 1.5× routeA（同 shape） | kernel-only 峰值 **1.27×**（w1/w3 @M=1024），全矩阵 0.35×–1.27× | **❌ 未达** |
| 大 shape ≥ 350 TFLOPS | run_bs 官方口径中位 **351.8**（351.0/351.8/376.4 三轮）；我方事件计时 347.1；冷机复测（冒烟轮）383.3 | **⚠️ 临界通过**（方差 ±9%，见 §4） |
| 端到端（含 A 量化） | routeB **全面落后**：0.37×–1.02× | **❌ 未达** |

**一句话结论：在干净 GPU、kernel-only 口径下，routeA（vLLM cutlass_scaled_fp4_mm）实测 155–313 TFLOPS，远快于克隆测试的 57–130（那是生产同机高压 + 含量化口径）；routeB 仅在 M∈[1024,4096] 的 w1/w3 窗口领先 12–27%，端到端因量化实现差距全面落后。P4 判据未达，建议维持 routeA 现役，routeB 不进入灰度。**

三个此前未知的重要发现（对后续决策有实质影响）：
1. **routeB 在 M=16384 崩塌至 0.35×**（108 TFLOPS，数值仍正确，全新编译复现）——超大 prefill 批次是 routeB 的禁区；
2. **K-heavy shape（K=14336 的 dense 投影）routeB 只有 94–143 TFLOPS（0.42×–0.60×）**——非 MoE 投影不可用 routeB；
3. **routeB 端到端的瓶颈不在 GEMM 而在 A 量化**：vLLM 的 C++ 单 pass 量化 ~200GB/s，triton 实现存在 layout 病理（20GB/s，已定位到 PTX 级并给出 94–136GB/s 的双 pass 修复），量化不补齐则 E2E 永远落后。

## 1. 测试环境与方法论

### 1.1 两条被测路径

| | routeB | routeA |
|---|---|---|
| 实现 | CUTLASS CuTe DSL 官方 SM120 pingpong blockscaled GEMM（vendored 三件套，routeb_official/） | vLLM `cutlass_scaled_fp4_mm` + `scaled_fp4_quant`（C++ 算子），经生产适配层 `RouteA` 类（`<INSTALL_DIR>/nvfp4/kernel1/nvfp4_4w4a_mmaf.py`，md5 2d9cda46 与四节点一致） |
| 数据格式 | MXF4：E2M1×E2M1 + UE8M0 32 组（sf_vec=32），C 输出 fp16 | NVFP4：E2M1 + E4M3 16 组，C 输出 bf16 |
| W 预处理 | 一次性量化打包（`torch_w_quant`，N 向 [N,K] 打包 + 逐行 32 组 SF swizzle） | 一次性 `preprocess_weights`（RouteA 类缓存 W，规避每次 ~7s 重预处理） |
| A 量化（E2E 口径） | K1+K2 双 pass triton（生产语义：32 组 UE8M0 + E2M1 打包 + MMA swizzle 直写，与 torch 参考逐位一致） | `torch.ops._C.scaled_fp4_quant`（vLLM C++，生产同款） |

### 1.2 口径定义

- **kernel-only（KO）**：纯 GEMM kernel 时间。cuda event 批内计时（warmup 10 + iters 30–50 × 3–5 轮取中位），warm-L2（两 route 同口径）。routeB 计时循环与我方管线同对象；与官方 `testing.benchmark` 口径在探针 P7 对照为 **0.984 比值**（<2% 偏差）。
- **端到端（E2E）**：A 量化 + GEMM 全链路（W 预处理均为一次性、排除在稳态外）。输入激活统一 fp16 [M,K]（routeA 生产路径 `A.float().half()` 之后的形态）；routeA 的 alpha/global_scale 张量预建（对 routeA 有利方向，保守判定我方门槛）。
- 输出 dtype：routeB fp16 / routeA bf16（均 16-bit，等价成本）；双方均不含输出后转换。

### 1.3 正确性保障（性能数字可信的前提）

- **布局验证探针（probe2_layout.py，全部通过）**：fp4 打包 = 紧凑行布局（行 m 起始偏移 m×K/2，低半字节=偶元素）与官方 `cute_tensor_like`+convert 路径**逐字节一致**；SF swizzle 映射（(m,kg)→(32,4,rest_m,4,rest_k,l) 列主序分解）与官方 `cvt_sf_MKL_to_M32x4xrm_K4xrk_L` 路径**逐字节一致**（stride 完全相同）；triton A 量化与 torch 参考逐位一致（±0 编码等价归一后 mismatch=0）；M=64 部分 tile 正确；编译对象跨 M 复用正确。
- **全矩阵数值校验**：每配置首个 M（≤4096）跑 `dequant_ref` 对照，全部 **rel_err ≤ 0.0004**（含双 pass 量化路径单独校验）；M=16384 崩塌档单独复测亦 rel_err=0.00035（慢但不错）。
- **GPU 干净度**：每轮 docker 前后 `nvidia-smi` 确认无其它计算进程；01 节点生产已停（停机窗口）。

### 1.4 与克隆测试（57–130 TFLOPS）的口径差异说明

nvfp4-clone-prod-test-20260820 的 routeA 57–130 TFLOPS 测于**生产 rank0 同机运行的高压 GPU 环境**（其报告 §四自述），且基准脚本含每次调用的量化与封装开销。本报告为**干净 GPU、kernel-only** 口径——routeA 实测 155–313 TFLOPS 与克隆数字不矛盾，是口径差。**precheck 的 ≥1.5× 判据当时是按克隆口径校准的**；以干净口径衡量，门槛实际被大幅抬高。建议决策层知悉此口径差后再裁决。

## 5. routeB tile 选优过程（如实记录）

- 候选：tile {128×128×128, 128×128×256} × epi {128×128, 64×32}，4 个 shape 配置 × 4 组合。
- **tile_k=256 全部编译失败**：DSL 报 `tCrSFA_copy_view_filtered` 布局 congruence 错误（vendored pingpong L944）——**MXF4（sf_vec=32）路径下 tile_k 固定为 128**，128×128×256 名义允许但实际不可用。tile 空间实际锁定 128×128×128。
- epi 128×128 在 M≥1024 一致优于 64×32（+3~7%）；小 M 差异 <2%。全部配置选 128³ + epi 128×128。
- sweep 代表值（KO TFLOPS）：w1@M=4096 321.0（epi 128×128）vs 305.5（64×32）；bigN@M=4096 360.8 vs 356.5；bigK@M=4096 142.8 vs <RING_SUBNET>。
- 选优均在 M=4096 定档（各 M 档相对排序一致，无翻转）。

## 6. routeB A 量化 kernel 工程备注（重要技术资产）

E2E 口径最初用"单融合 triton kernel（量化+打包+SF swizzle）"，实测仅 **~20GB/s**（M=4096 时 2.2ms，vLLM C++ 同工作 0.22ms）。系统性归因（quant_tune1–8 共 8 轮微基准，全部留档）：

1. **根因（PTX 级实证，quant_ptx_diag.py）**：归约（`tl.max` 组内 max）+ broadcast（scale 除法/乘法）与 7 段阈值比较链合核时，triton layout 规划器将 A 加载从 `ld.global.v4.b32`（16B 向量化）降级为**标量 `ld.global`（2B/线程）**，内存吞吐崩 10×。无寄存器溢出（n_regs=66/n_spills=0）、与 BLOCK_M/warps/fp16-fp32/evict 策略无关；各子集单独成核均 ~200GB/s，仅特定组合触发病理。
2. **修复（已采纳进 E2E 主路径）**：拆成 K1（SF pass：组 max → E8M0 → 逻辑布局 SF）+ K2（量化 pass：A + SF → E2M1 打包直写 kernel buffer + SF swizzle 直写），两核各自保持向量化加载，合计 **94–136GB/s**（较病理版快 5×）。K2 数值与 torch 参考**逐位一致**（mismatch 0/524288，±0 编码等价归一后）。
3. **遗留差距**：双 pass 读 A 两遍，理论上限 ~单 pass 一半；对标 vLLM C++ 单 pass ~200GB/s 仍有 1.5–2× 差距。行动项 A1：生产集成若走 routeB，量化需（a）C++/CUDA 单 pass 实现，或（b）向 triton 上游报 layout 病理（已有最小复现），或（c）CUDA graph 消除小 M launch 开销。

### 7.1 P4 判据裁决

| 判据 | 数据 | 裁决 |

| routeB ≥1.5× routeA | KO 峰值 1.27×；E2E 峰值 0.97× | **未达** |

### 7.2 若决策层仍要榨取 routeB 残余价值（条件路线，非本报告建议）

- 唯一理论窗口：w1/w3 prefill、M∈[1024,4096]、**且**行动项 A1（量化达 ~200GB/s 单 pass）落地后，E2E 或可到 ~1.05–1.2×——收益 5–20%，远低于 1.5× 预期，需重新评估投入产出。
- 插件分派规则（若实施）：`M < 256 → B12X`（维持）；`256 ≤ M ≤ 8192 且 shape ∈ {w1,w2,w3 类} → 视 A1 落地情况`；`M > 8192 或 K ≥ 14336 → routeA`（routeB 崩塌区）。

### 7.3 行动项

### 7.4 对 P3/插件侧的移交信息

- routeB GEMM 数值管线（含双 pass 量化）在全部测过的 shape/M 组合 rel_err ≤ 0.0004——P3 的真实权重语义验证可与本报告的管线代码直配；
