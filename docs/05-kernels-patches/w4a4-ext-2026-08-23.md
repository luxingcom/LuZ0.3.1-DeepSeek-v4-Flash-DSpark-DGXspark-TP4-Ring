## 1. 并发 PR 基准方法论（新增能力）

### 1.1 工具

`/tmp/_w4a4_ext/concurrent_prefill.py`（本地副本 `_w4a4_ext_assets/`）：
- asyncio + aiohttp，N 并发客户端同发枪（共同 t0），panorama 同款 prompt 构造（4K 档 = 4096 字符 FOX ≈ 8.2K tok，每客户端唯一 nonce 防前缀缓存命中）
- **聚合吞吐口径**：`agg_tps = Σ(prompt_tokens_i) / (max(done_i) − t0)`——衡量集群在并发 prefill 负载下的总完成速率
- 输出每轮聚合 tok/s + 各客户端 TTFT 分布（min/med/max）
- **单客户端校准**：C1 档 2773 vs panorama 同窗口 2769——与既有口径一致 ✓

### 1.2 基础观察（B1 臂，W4A16）

并发聚合吞吐 ≈ 单流吞吐（C6 2744 / C12 2737 vs 单流 2769，效率 99%）——**prefill 已计算饱和**，并发不增吞吐也不塌；TTFT 随排队位置阶梯分布（C12：4.4s → 21s → 36s），符合 4096 分块调度轮转预期。这一饱和特性使并发聚合吞吐成为检验"单位计算效率增益"的干净标尺：任何 W4A4 kernel 效率增益应直接表现为聚合数字抬升（无需担心调度空转稀释）。

## 5. 工程发现与行动项

### 5.1 工程发现

1. **systemd 服务 stop ≠ 容器停**：vllm-tp4-head/worker.service 的 ExecStart 是 monitor（`docker wait` 跟随），停服务不停容器。正确重启姿势 = **服务保持 active + `docker rm -f vllm-tp4-rank0` 触发 head-first 全链重建**（monitor 清 worker 容器 → 各机 systemd 自愈重建，worker 带 head TCPStore 门禁防冷启动互杀）。本次三臂全部走此路径，零人工干预。runbook 建议补此条（与 phase3b §3.2.2 教训合并：**重启 = 杀 rank0 容器；恢复自愈链 = 确认 head + 三 worker + healthcheck.timer 三件套**）。
2. **8192 引发 KV 每token足迹 +58%**（9.0→14.2 KiB/tok）：非激活/CUDAGraph 固定开销可解释（那两项仅 +1.9 GiB），48.19 GiB KV 预算按原足迹应得 5.4M tokens 实得 3.48M——机制待查（疑似 batched 8192 下 attention/KV 页布局变化）。这是 threshold 8192 方向的独立于性能的第二重否决证据。
3. **greedy 门 prompt 集需清洗**：reason/zh 两 prompt 在同配置背靠背运行间不稳定（概率投机解码运行级非确定），phase3b 已有先例（code prompt 单 token 自复跑不稳）。不稳定 prompt 会产生假 No-Go 信号（本日 B2 初判即被触发）。
4. checker（check_vllm_script.sh）需要脚本路径参数，无参调用静默退出——误报 FAIL 一次，已修正调用方式。
