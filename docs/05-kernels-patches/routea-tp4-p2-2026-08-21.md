## 3. T1 hybrid 失败证据链（两次）

1. **第一次（util=0.80 生产配置）**：`Using W4A4B12xExperts` 确认插件生效 → 权重加载完成 → `ValueError: No available memory for the cache blocks`（kv_cache_utils.py:758）——hybrid 双表示（W4A4 payload 副本 + W4A16 打包）+42GB 使 0.80×121.63=97.3GB 预算无 KV 余量。与 P1 预估一致（mini 实测 +15.5GB/4 层 TP1 折算 +41GB/rank）。
2. **第二次（util=0.92）**：`check_vllm_script.sh` 前置自检拒绝——`✗ 缺关键参数: gpu-memory-utilization 0.80`（生产关键参数 pinned 校验）。修改 checker 属生产护栏变更，超出本测试授权，中止该路径。
3. **即使可启动的预期**：T1 的 W4A4 分支走与 T2 相同的 wrapper CG=1 路径 → prefill 大概率同样 -13%（T2 已证），T1 无独立翻盘可能。

## 4. 根因分析：kernel 1.32× 为何没穿越到端到端

Task #20 微基准（probe15/16）：wrapper use_cuda_graph=**False** → `select_sm120_moe_backend(num_tokens)` 按 M 动态选 micro/static/dynamic backend → M=4096 时 W4A4 1.32×。
生产插件（CG=**1**，decode cudagraph 捕获所需）：wrapper run() 在 use_cuda_graph=True 下绑定预分配 workspace（static 或已分配的 dynamic）——大 M 走 static workspace 路径，性能显著低于动态路径；叠加 wrapper 每层工作区显存（43 层 × wrapper buffers + scale 双份存储 → weight +28GB，远超 P1 线性外推的 +8.7GB）。端到端 prefill 中 MoE 份额再打折 → 净效果 -13%。
decode 回退（-16~-19%）：full 模式 decode 走 wrapper（微基准 M=1 时 6.2× 的收益同样来自 micro/dynamic 动态选择路径；CG=1 static 路径无此收益），且 12 并发稳态 64.9 tps 中还含首 rep JIT 拖累（36 tps）。

后续路径（按投入产出排序，供团队裁决）：
1. **wrapper 动态路径复测（低成本，1 天）**：hybrid-only + CG=0 wrapper（W4A4 只服务 M≥3072 的 prefill——vLLM cudagraph 捕获尺寸 ≤96，W4A4 分支永不进捕获，CG=0 理论可行）+ T1 内存解法（改 checker 护栏或 `--kv-cache-memory` 显式预算）。**预期收益上限有限**：即使 MoE kernel 1.32×，端到端 prefill 折算 ~+10-13%（MoE 份额假设 40-50%），贴近 ≥15% 判据下限——需先确认是否值得动内存护栏。
2. **上游跟踪**：b12x/flashinfer 的 static workspace 路径大 M 性能与 workspace 显存优化（weight +28GB 的一半来自 wrapper 工作区）。
3. **保持现状**：B12X W4A16 路径已被三运行对照确认为当前最优生产配置。
