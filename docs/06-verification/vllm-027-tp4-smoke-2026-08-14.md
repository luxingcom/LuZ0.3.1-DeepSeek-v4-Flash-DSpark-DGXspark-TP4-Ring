## 3. 验证结果明细

### 3.1 环境核实（全部就位）
- 镜像：01 本地已有 + registry(<NODE_IP>:5000) 已缓存 → 02/03/04 直接 pull，digest 一致。
- 权重：01/02 `/home/<USER>/models/deepseek-v4-flash-0731-nvfp4`（本地 165GiB）；03/04 `<MODELS_DIR>/deepseek-v4-flash-0731-nvfp4`（NFS 只读挂载，<NODE_IP> / <NODE_IP>）。
- 模型 config：`model_type=deepseek_v4`，`expert_dtype=fp4`，dspark_block_size=5，markov_rank=256，target_layers [40,41,42]。

### 3.2 分布式与加载（全部通过）
- `world_size=4 rank=0/1/2/3 local_rank=0 backend=nccl` 四机均确认。
- `vLLM is using nccl==2.30.7`（与生产 ring-only 同版本）。
- `Loading safetensors checkpoint shards: 100%`（48 shards，244.08s）。
- `Detected ModelOpt NVFP4 checkpoint (quant_algo=NVFP4)`。
- `Using MoEPrepareAndFinalizeNoDPEPModular`，`Using Eagle3 auxiliary layers from config: (41, 42, 43)`。
- `Using fp8_ds_mla data type to store kv cache`。

### 3.3 排查链（按序解决）
1. **GLOO connectFullMesh 127.0.1.1 失败** → 根因：03/04 的 /etc/hosts 将 hostname 指向 127.0.1.1；修复 `GLOO_SOCKET_IFNAME=enP7s7`。
2. **NCCL 跨机失败** → 先用 `NCCL_IB_DISABLE=1` 走 TCP 管理网跑通功能（未叠加 ring-only/LD_PRELOAD）。
3. **follower EngineCore collective_rpc 断言** → 根因：worker 必须 `--headless`（多机 PP/TP headless 模式），避免启动 API server/EngineCore 集体初始化路径。
4. **deep_gemm 权重后处理 tvm_ffi 崩溃** → `--linear-backend cutlass`（避开 deep_gemm）。
5. **moe_backend=flashinfer_b12x 拒绝**（swiglu_limit=10.0 需 clamp）→ `--moe-backend flashinfer_cutlass`（vLLM 明确提示）。
6. **MHC tilelang/deep_gemm "no interpreter set" 崩溃** → patch `mhc_pre_broadcast_tilelang`（0.27 唯一无 guard 的 deep_gemm 调用点）+ `VLLM_USE_DEEP_GEMM=0`，torch fallback。补丁文件：`<INSTALL_DIR>/scripts/v027-test/patch/mhc/tilelang.py`（md5 69107d80ca68d8daefe90761762efcdd）。

### 3.4 最终阻塞点（镜像内核缺陷）
模型 attention QKV 为 **block-scale FP8**，`_POSSIBLE_FP8_BLOCK_KERNELS` 全部 backend 在 sm_121 上均失败：

| backend | 结果 |
|---|---|
| deep_gemm | ❌ tvm_ffi "cannot access PyObject for Tensor - no interpreter set"（torch 2.13 PyObjectSlot 严格检查） |
| flashinfer_cutlass | ❌ "FlashInfer block-scale FP8 GEMM is not available" |
| cutlass | ❌ `dispatch_scaled_mm` 运行时 dispatch 失败 |
| triton | ❌ dtype canonicalization KeyError |
| humming | ❌ `ModuleNotFoundError: No module named humming` |

另：torch `_clear_torch_ops_cache` 存在间歇性 `UnicodeDecodeError`（op registry use-after-free 竞态，位置 ~180 随机字节），多在进程清理期出现，属 torch 2.13 稳定性问题，未影响主路径判定。

## 5. 遗留问题 / 根因结论

**根因：test-0.2.1-v027 镜像（0.27.2.dev + NGC 26.07/torch 2.13）在 sm_121 上 block-scale FP8 scaled_mm 内核构建不完整/不兼容**。多个 backend（deep_gemm/flashinfer/cutlass/triton/humming）全部不可用，非部署参数可解决。这需要**重建镜像**（正确编译 sm_121 的 scaled_mm 内核）或等待官方 vLLM 0.27 GB10 镜像。

次要问题：
1. torch 2.13 `_clear_torch_ops_cache` UnicodeDecodeError（间歇性，进程清理期）。
2. 生产 0.26 的 `/opt/nccl-ringonly` + libncclpin LD_PRELOAD 与 0.27 新通信模式的交互仍未验证（本测试全程未叠加，用 TCP 绕开）。

## 7. 建议

1. **阻断 vLLM 0.27 生产切换**：test 镜像的 block-scale FP8 scaled_mm 内核在 sm_121 上不可用，需镜像重建。
2. 重建时重点验证：① CutlassFp8BlockScaledMMKernel 的 sm_121 dispatch；② deep_gemm TVM FFI 与 torch 2.13 的 interpreter 兼容；③ 安装 humming 包或移除其对 kernel 注册的影响。
3. 修复 torch 2.13 `_clear_torch_ops_cache` 竞态（可考虑 patch torch/library.py 捕获 UnicodeDecodeError）。
4. NCCL：后续应单独验证 ring-only 补丁在 0.27 的 LD_PRELOAD 截获（P0 风险项），TCP 模式仅作功能验证。
