# LiteLLM 4000 层开销核实报告（严格同条件 A/B 验证）

**日期**：2026-08-06（UTC 10:28–10:55）
**测试**：Tessa（测试专家）
**结论（TL;DR）**：**此前 4000 网关 vs 直连 8001 的 ~23-24% 开销不成立**。严格同条件交错 A/B 下，经 LiteLLM 4000 的真实开销为 **-6.8% ~ +6.9%（中位 ~+0.5%）**，TTFT 开销中位 ~0%。原 23% 数据系**测试口径不一致**（直连基线用短 prompt+temp0.6，经网关用 PARA 填充 512 ctx+temp0.7），非网关层真实开销。

## 1. 测试方法（严格同条件 A/B）

| 项 | A 组（直连 8001） | B 组（经 4000） |
|---|---|---|
| 端点 | `http://<NODE_IP>:8001/v1` | `http://127.0.0.1:4000/v1` |
| model | `deepseek-v4-flash-0731` | `dspark-prob`（上游指向同一 8001） |
| key | `<API_KEY>-1128…` | `sk-07E13j…` |
| 参数 | temp 0.7 / 流式 + usage | temp 0.7（config 已固定） / 流式 + usage |

- 同 prompt 集（原 gw4000 的 code/json 集）、同脚本、同参数
- **交错**：每 cell 3 轮 A/B 交替（轮间切换 A→B / B→A 顺序），避免 vLLM 状态漂移；每轮测量前热机 1 次
- 负载：short ctx200→max64、medium ctx2048→max256，并发 c1/c5；另加 **ctx512→max128 c5 精确复现原声称条件**
- 指标：TTFT / 聚合输出吞吐（agg t/s）/ TPOT / 总耗时；记录每请求 usage
- 开销% = (A - B)/A（负值 = B 更快）

## 3. 开销来源分析

1. **LiteLLM 处理延迟（固定每请求）**：❌ 无证据。TTFT 中位开销 ~0%（-4.6% ~ +4.5%），B 组 TTFT 未系统性高于 A 组 → 鉴权/路由/日志不构成可观固定延迟。
2. **并发调度瓶颈（单进程 asyncio）**：❌ 无证据。c5 开销（+0.2% ~ +5.0%）与 c1（-6.8% ~ +1.3%）无系统性差异；LiteLLM 单进程在 c5 下未显现劣化。
3. **spend 追踪写 PG**：✅ 确认**异步**。单请求后立即查 count 不增（638→638），批写 2s 内落库（10 请求 +8）；全测试 639→788（+149 行匹配 ~150 个 B 组请求）。非同步阻塞路径。
4. **日志**：uvicorn access 日志仅请求行，无 duration；config.yaml 无 success_callback/消息日志开关（仅 drop_params/num_retries/request_timeout）。

## 4. 结论

1. **开销是否真实**：**同条件下经 4000 的真实开销为 -6.8% ~ +6.9%（中位 ~+0.5%），TTFT 中位 ~0%**。此前 23-24% 不成立，属**测试口径差异**（详见 §5）。
2. **开销来源**：固定每请求开销 ❌、并发瓶颈 ❌、spend 异步写 ✅ 无阻塞、日志无开销 → **LiteLLM 层在当前配置下无显著可测开销**；剩余 ±5% 在轮间噪声范围内（历史 c5 波动 ±10% 常见）。
3. **优化建议**：当前配置**无需为开销优化**。若要进一步压低残余波动可考虑（非必要）：
   - 保持 spend 异步写入现状（已是异步，无需改）；
   - 如需极低延迟可评估 `turn_off_message_logging` 或日志降级，但证据显示收益 < 可测噪声；
   - 多 worker（uvicorn workers>1）仅在 >c5 高并发下才可能有收益，当前无需求。

## 5. 原 23% 数据的口径差异（根因）

| 项 | 原直连基线（bench-f-baseline 08-05） | 原经网关（bench-gw4000 08-06） |
|---|---|---|
| prompt | **短 prompt，无 PARA 填充**（`<rnd>`+负载指令，~50 tokens） | **PARA 填充至 ctx=512** |
| temperature | **0.6** | **0.7** |
| 结果 | code 131.8 / json 122.5 t/s | code 101.2 / json 93.5 t/s |

- 两变量都压低经网关侧吞吐：长前缀增加 prefill 摊薄、temp 0.7 采样多样性略降 decode 效率
- 本文 §2.3 证明：**短 prompt + temp 0.6 在直连 8001 今日仍产出 126.8/114.5 t/s**（接近原基线）
- 本文 §2.2 证明：**PARA 512 + temp 0.7 下，直连与经网关几乎无差（code -0.89%）** → 差异来自 prompt/temp，与网关无关
