## 2. 全矩阵速览（三类型 × 五档位 × 三并发 = 45）

| 档位 | prefill (c1) | decode (c1) | TTFT (c5) | TPOT (c5) | 类型差异 |

| 512 | 1591-1597 | 60-118 | 0.96-1.11 | 0.025-0.042 | prose decode 仅 coding 的 ~50% |
| 2048 | 2150-2217 | 58-118 | 2.75-3.34 | 0.025-0.041 | 同上 |

- coding ≈ json（decode 110-122 同档）：结构化续写投机收益高

## 3. 核心异常①：131072×c5 decode 断崖（7.8/8.2/4.2 tok/s）

### 3.1 定量拆解（机制定位）

```
MLA KV = 6.7 KB/token（项目实测压缩后）
131072 ctx → 单请求 KV = 878 MB
c5 并发 → 每 decode 步需遍历 5 × 878 MB = 4.39 GB KV
TPOT p50（coding c5）= 0.128s → 等效瞬时带宽 = 4.39 GB / 0.128s ≈ 34 GB/s
UMA 有效带宽（PMU 实测）= ~643 GB/s → 利用率仅 ~5%
```

**结论：不是带宽饱和，是"每步串行遍历 4.4GB KV 的访存延迟"（memory-latency-bound）**——与 8/12 对 768K 单流的诊断同源，只是这次是 131K × 5 并发放大。

### 3.2 为什么是"断崖"而不是"渐变"

| 档位 | c5/c1 decode 扩展比 | 每步 KV 遍历总量（c5） |
|---|---|---|
| 512 | 1.7-1.9×（亚线性） | 17 MB |
| 8192 | ~1.5× | 274 MB |
| 32768 | ~0.9× | 1.1 GB |
| 131072 | **0.35×** | **4.4 GB** |

- 每新增并发请求的 KV 遍历**边际成本随 ctx 线性增长**，而 UMA 带宽/延迟固定
- 131072 档：5 并发总遍历 4.4GB/步，已超过 SM 访存隐藏能力的**临界点**——多一个请求不仅不赚，还把每步延迟从 9ms 拉到 128ms（14 倍）
- 128ms/步 × 88 层结构 → 单 token 端到端 128ms = 7.8 tok/s ✓（与实测吻合）

### 3.3 投机解码在断崖中"无辜"

131072×c5 时 acc 仍 0.86/0.92（高）——**断崖不是投机失效，是并发 × KV 遍历**。投机草稿与主模型共享同一 KV，接受率高时草稿开销被摊薄，但主模型每步 4.4GB 遍历才是瓶颈。

### 3.4 对策建议

| 方案 | 可行性 | 预期 |
|---|---|---|
| **长档并发上限**：>64K ctx 请求动态限流（vLLM 调度层按 ctx 长度分配 seqs 槽位） | 中（需 vLLM 侧开发） | 消除断崖 |
| **KV 优先级抢占**：长请求让出连续生成（短请求插入） | 低-中 | 摊薄长档步延迟 |
| **投机草稿深度随 ctx 缩放**：131K 档降 draft 数 | 低 | 边际（主模型遍历仍是瓶颈） |
| **接受现状**：长档用 c1（110-115 tok/s 已接近 c3 的 134-145 可用性） | ✅ 立即 | 生产指引即可 |

**生产指引（立即生效）**：>64K 上下文请求建议并发 ≤1（c1 档 decode 110+ 与 c3 差距 <30%）；>32K 建议 ≤c3。

## 4. 核心异常②：32768×c5 反噬（TPS 105-109 < c3 138-141）

- decode 46→21（coding）/47→22（json），TPOT 0.022→0.048s（**翻倍**）
- TPS = decode × 并发：c3 = 46×3 = 138 ✓；c5 = 21×5 = 105 ✗——**decode 掉速超过并发增益**
- 拐点判定：32768 档第 4/5 并发请求的 KV 遍历边际成本（+1GB/步）> 该请求的并发吞吐收益
- **与 131K 断崖同一机制、不同位置**——32768 是"临界点前 1 档"，131072 是"越过后 2 档"

**通用规律（本集群）**：最优并发点随 ctx 单调递减——512-8K 用 c5（176-202 TPS）、32K 用 c3（138-141）、128K 用 c1（110-115）。

## 5. 网络质量视角（CAT 专项）

| 项 | 实测/分析 | 判定 |
|---|---|---|
| 网络是否瓶颈 | decode 断崖期间网络仅 ~10% 利用率（8/12 实测 22GB/s 双向、有效单向 11.67GB/s）；TP=4 all-reduce 每步 368KB×5 请求 < 2MB | 🟢 网络余量巨大，非瓶颈 |
| NFS 恢复（RoCE 双源） | 03←<NODE_IP>（环网 module0）、04←<NODE_IP>；加载 117-136s（<270s 门禁）→ 等效 ~1.3GB/s（156GB/117s） | 🟢 远低于 RoCE 200G 能力 |
| nconnect=4 + hard + timeo=600 | 多连接并发 + 硬挂载长超时，防 NFS 抖动传播到 GPU 加载 | 🟢 配置合理 |
| 长档排队对 TTFT | 131K TTFT c1 57.4 → c3 143 → c5 183s（3.2×）——prefill 是 GPU 计算型（非网络） | 🟢 网络无关 |

**结论**：所有测试异常均可归因于 **GPU 侧 UMA 访存延迟 + 调度**，**无任何网络质量因素**。四机 RoCE 环网（路径 A/B 双通道、MTU 9000、QoS DSCP46→P5）在测试中零错误零丢包，NFS 双源恢复后加载稳定。
