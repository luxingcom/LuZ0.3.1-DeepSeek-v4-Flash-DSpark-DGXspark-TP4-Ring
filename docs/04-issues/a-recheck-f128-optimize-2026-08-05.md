## ⚙️ 二、F 方案 seqs=128 验证（Rex）

### 显存预算评估（可行，无 OOM）
- 权重 78.98 + 激活 1.73（与 seqs=6 相同）+ non-torch 4.11 + CUDAGraph 0.7 ≈ 98 GiB
- KV pool **12.48 GiB / 1.95M tokens**（seqs=6 为 13.0 GiB/1.99M）——几乎不变，证实 KV pool 是 gpu_memory_utilization 内存边界而非 seqs×ctx 需求边界
- **关键副作用**：max_num_scheduled_tokens 由 2024 降至 **1536**（vLLM 按 spec decoding 计算），单步 batch 容量变小 ← 性能下降主因

### 性能对比（F128 vs F seqs=6 基线）
| 指标 | seqs=6 基线 | seqs=128 | 变化 |
|------|-----------|----------|------|
| c5 聚合 | 87.2 t/s | **56.7** | **-35%** |
| c10 聚合 | （无基线） | 65.3 | 仍低于 seqs=6 的 c5 87.2 |
| c1 单流 decode | 39.6 t/s | **30.15** | **-24%** |

- 0 OOM / 0 CUDA error（KV 峰值占用 0.3%），healthy ~5min READY

### 结论与建议
- **F 维持 seqs=6 生产正确**；seqs=128 是负优化（scheduled-tokens 预算降低 + 长上下文加剧抢占）
- 后续并发优化方向：**提高 max_num_batched_tokens / max-num-scheduled-tokens**（而非 seqs），或降 ctx 400K 换更大 KV pool
- **A/C 的 seqs=128 高吞吐结论不能直接迁移到 F**（fp8/hybrid 栈 vs nvfp4_ds_mla+DSpark 栈的 spec-token 预算逻辑不同）
